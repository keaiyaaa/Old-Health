**为什么不现在就手写 `openapi.yaml`**：

1. 手写 OpenAPI 与手写接口文档是**两份需要同步维护的内容**，在技术栈未定时手写，等选型后大概率要重写
2. 正确做法是**由后端代码生成**，保证契约与实现天然一致
3. 后端技术栈（`../../planning/待确认事项.md` C2）未定，生成工具链也就无法确定

**因此：在后端选型确认前，不要在此目录添加手写的 OpenAPI 文件。** 手写生成的契约会立刻与实现分叉，比没有更糟。

## 2. 生成方案（待 C2 确认后执行）

### 2.1 按技术栈选择生成方式

| 后端技术栈 | 生成方式 | 工具 |
|---|---|---|
| Python / FastAPI | 从代码注解自动生成 | FastAPI 内置 `openapi.json` |
| Node / NestJS | 从装饰器生成 | `@nestjs/swagger` |
| Java / Spring Boot | 从注解生成 | `springdoc-openapi` |
| Go | 从结构体注解生成 | `swaggo/swag` |

**统一要求**：生成物为 **OpenAPI 3.1**，输出到本目录。

### 2.2 生成物命名

```
openapi/
├── README.md          ← 本文件
├── openapi.yaml       ← 生成物（唯一契约文件）
└── .generated         ← 标记文件，内容为生成命令与时间
```

## 3. 硬规则

| # | 规则 |
|---|---|
| 1 | **禁止手工修改生成文件。** 任何修改都会在下次生成时被覆盖 |
| 2 | 生成文件头部必须包含 `# AUTO-GENERATED — DO NOT EDIT` |
| 3 | 需要改契约时，**改后端代码注解**，然后重新生成 |
| 4 | 生成物必须提交到仓库（便于前端在无后端环境下生成类型） |
| 5 | 生成物与 `../API-0x-*.md` 不一致时，**以人读文档为准**，并修代码 |

### 3.1 为什么生成物要提交到仓库

前端可以在没有后端运行的情况下从 `openapi.yaml` 生成类型定义。这对"后端未就绪，前端先开发"的场景（`../../PROJECT_REQUIREMENTS.md` 14.2 A3）是必需的。

## 4. CI 校验要求

在后端接入后，CI 必须包含以下步骤：

```
1. 重新生成 openapi.yaml
2. git diff --exit-code openapi/openapi.yaml
   → 有差异说明生成物与代码不一致（有人手改了，或忘了重新生成）→ 构建失败
3. 契约兼容性检查（对比上一版本）
   → 检出破坏性变更（删除字段、改类型、改必填性）→ 构建失败，除非同时升了 API 版本
4. 契约测试
   → 用 openapi.yaml 校验实际接口响应结构 → 不匹配即失败
5. 合规字段黑名单扫描
   → 扫描 openapi.yaml，断言以下字段名不出现：
     zScore, mean, stdDev, probability, score, riskLevel,
     mocaB, mmse, fluencyScore, interpretation, conclusion
   → 出现即失败
```

**第 5 步是本项目特有的**，不是通用 OpenAPI 实践。它把"不返回内部统计量与量表分数"这条合规红线做成了**构建期强制检查**，而不是靠人工评审。

## 5. 与文档的分工

| 内容 | 写在哪 | 谁维护 |
|---|---|---|
| 接口设计意图、为什么这样设计 | `../API-0x-*.md` | 人 |
| 合规约束与理由 | `../API-0x-*.md` | 人 |
| 变更流程 | `../README.md` | 人 |
| 字段类型、必填性、枚举、示例 | `openapi.yaml` | **代码生成** |
| 客户端类型定义 | 由 `openapi.yaml` 生成到客户端 | 工具 |

**一句话**：**人读文档写"为什么"，OpenAPI 写"是什么"。** 两者职责不重叠，避免重复维护。
