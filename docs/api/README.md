## 1. 唯一事实来源声明

**`docs/api/` 是前后端共同遵循的唯一接口事实来源。**

| 规则 | 说明 |
|---|---|
| ✅ 接口定义只写在这里 | 全部接口、字段、错误码都在本目录 |
| ❌ **禁止**在 `../frontend/` 下建接口文档 | 前端只声明"依赖哪个接口" |
| ❌ **禁止**在 `../backend/` 下建接口文档 | 后端只声明"实现哪个接口" |
| ❌ **禁止**手工修改生成文件 | `openapi/` 下由后端生成的产物不得手改，见 `openapi/README.md` |
| ⚠️ 代码与本文档不一致 | **以本文档为准**，改代码；若确认文档有误，先改文档再改代码 |

**为什么这条规则要写在最前面**：前后端各维护一套接口文档，是并行开发中最常见的失败模式。两份文档在两周内必然分叉，然后团队花更多时间争论"以哪个为准"，而不是写代码。

## 4. 契约设计的 12 条原则

来自 `../PROJECT_REQUIREMENTS.md` 第 10 章，这里展开成可执行的约束：

| # | 原则 | 落地要求 |
|---|---|---|
| 1 | **服务端返回文案 key，不返回整句文案** | 状态机只返回 `copyKey`；前端从 `ui/copy/` 渲染 |
| 2 | **指标返回原始数值，但不在任何接口暴露内部统计量** | 返回 `value`，**不返回** `zScore` / `mean` / `stdDev` |
| 3 | **所有时间用毫秒时间戳** | `number`（int64），不用字符串日期 |
| 4 | **可为空字段显式声明** | 文本指标在 ASR 失败时为 `null`，不是 0、不是省略 |
| 5 | **音频不走业务服务器** | 预签名 URL 直传对象存储 |
| 6 | **写操作幂等** | 上传登记、导出、标注均需 `Idempotency-Key` |
| 7 | **列表统一游标分页** | 不用 offset 分页，避免深分页性能问题 |
| 8 | **版本走 URL 前缀** | `/v1/...`；破坏性变更升 `/v2` |
| 9 | **错误结构统一** | `{ code, message, requestId, details? }` |
| 10 | **限流按 IP + 账号 + 接口三维** | 高风险接口更严 |
| 11 | **越权返回 404 而非 403** | 防资源存在性探测 |
| 12 | **禁止存在面向医生的临床输出接口** | 见 `../PROJECT_REQUIREMENTS.md` 9.2.4 |

**第 12 条是合规硬约束**，不是风格偏好。任何新增接口如果返回"临床判断/风险分级/检查建议"，一律拒绝。

## 5. 接口文档的固定结构

每个 `API-0x-*.md` 必须包含：

1. 业务域说明与对应的后端模块
2. 通用约定（该域特有的）
3. 接口清单表
4. 每个接口的：方法、路径、权限、请求参数、请求体、响应体、错误码、幂等、限流
5. 该域的合规约束（如有）

## 6. 与 OpenAPI 的关系

| 问题 | 答案 |
|---|---|
| 谁先写？ | **先写本文档（人读）**，再由后端生成 OpenAPI（机读） |
| 不一致怎么办？ | 以本文档为准；生成物由 CI 校验，不一致即构建失败 |
| 前端怎么用？ | 前端从 `openapi/` 生成类型定义，**不手写请求类型** |
| 能直接改生成物吗？ | **不能**。见 `openapi/README.md` |

## 7. 契约变更流程

```
1. 先改 docs/api/ 下的接口文档；**涉及字段的新增/修改，必须同时更新 字段设计表.md**（字段层唯一事实来源，见该表第 6 节四处联动）
2. 更新 openapi/（或由后端重新生成）
3. 同步更新 docs/frontend/modules/ 与 docs/backend/modules/ 中受影响的小节
4. 更新 ../PROJECT_REQUIREMENTS.md 12.5 验收清单（如涉及验收）
5. 破坏性变更 → 升 API 版本，并保留旧版本至少一个迭代周期
6. 记录到 ../PROJECT_REQUIREMENTS.md 15.2 变更记录表
```

**禁止**：先改代码再补文档。那样文档永远追不上代码，等于没有文档。
