## 1. 项目背景、目标与范围

### 1.1 项目背景

担心父母认知退化的子女，目前只能靠"感觉"判断。医院记忆门诊一年一两次，中间的变化全部丢失；网上能找到的语音筛查工具都只给**一次性的判别结论**——既没有趋势，也直接触碰医疗器械红线。

本项目做的是这件事的另一半：**高频、被动、零负担地记录自然说话，只看个人纵向变化，永远不给结论。**

### 1.2 双重目标

**产品目标（C 端）**：让子女用一部手机、零门槛地持续记录父母的说话方式，在出现持续变化时获得"建议去做专业评估"的提示，同时**绝不给任何诊断结论**。

三层价值，按优先级：

1. **陪伴记录** —— 音频 + 转写文本，本身就是留给家人的家庭档案
2. **语言趋势** —— 相对个人基线的变化，不是绝对分数
3. **就医衔接** —— 把"提示"变成"带着材料去看医生"

**论文目标（方向一）**：利用预训练语音/语言模型，从自发语音中提取语言学与声学特征，实现 AD/MCI 分类或 MMSE 评分预测。技术栈 wav2vec 2.0（声学）+ BERT（文本）+ 双模态融合 + 参数高效微调（LoRA）。目标会议 ICASSP / Interspeech / IEEE BIBM / HIDA 2026。

### 1.3 目标冲突与取舍原则

| 冲突点 | 论文想要 | 产品要守 | 取舍 |
|---|---|---|---|
| MMSE 评分 | 模型输出 MMSE 预测值并展示 | 产品**绝不能**展示任何分数（合规红线） | **严格隔离**：研究模式可有，C 端物理上不可见 |
| 文本指标口径 | 用人工转录（ADReSS ground truth）训练 | 产品用 ASR 输出，有错字 | 产品侧文本指标标"估算值"；研究模式同时保存 ASR 文本与人工校订文本 |
| 任务范式 | Cookie Theft 图片描述（标准化、可比） | 老人日常自由叙述（依从性） | **双轨**：每日自由叙述（产品）+ 每周图片描述（研究），见 5.5 |
| 数据用途 | 需要长期、可标注的数据 | 用户要隐私、要能删 | 研究模式独立知情同意，可单独撤回 |

### 1.4 项目范围

**一期（MVP + 产品可用）**：Android 原生 App（老人端 + 家属端双模式）+ 云端后端（账号 / 对象存储 / 分析队列 / 境内 ASR）。覆盖 FR-1 至 FR-7 的 M 级与 S 级需求，FR-8 研究模式按路径 2 标准建设但不阻塞主线。

**不在范围**：见 1.5。

### 1.5 明确不做（Out of Scope）

这一节同时是**范围边界**和**合规边界**，任何一条被突破都需要走 15.2 的变更流程。

**合规红线类（永久不做）**

| # | 不做 | 理由 |
|---|---|---|
| X-1 | 不做诊断、确诊、筛查、风险评估、概率/置信度输出 | 落入医疗器械定义 |
| X-2 | 不输出任何量表分数（MMSE / MoCA / AD8 等），C 端一律不可见 | 同上；仅研究模式录入，不参与展示 |
| X-3 | 不做语音身份识别、声纹提取、说话人辨认 | 生物识别信息，额外合规负担 |
| X-4 | 不做认知训练、认知干预、康复训练 | 一旦提供干预措施即落入数字疗法/医疗器械 |
| X-5 | 不做在线问诊、处方、药品推荐、转诊挂号 | 需要医疗资质 |
| X-6 | 不做面向医生的结构化临床建议输出 | 见 9.2.4「就诊摘要边界」 |

**范围控制类（一期不做，二期可评估）**

| # | 不做 | 说明 |
|---|---|---|
| X-7 | iOS 版本 | 一期只做 Android；假设见 14.2 A1 |
| X-8 | 多语言（英语等） | 一期仅普通话 + 方言，ASR 与指标均按中文校准 |
| X-9 | 端侧 ASR 模型 | 走云端 ASR，避免 APK 体积与推理耗时 |
| X-10 | 视频、摄像头、照片采集 | 与语言指标无关，且大幅提高合规成本 |
| X-11 | 采集位置、通讯录、相册、设备标识等无关权限 | 权限最小化 |
| X-12 | 社交功能（家庭群、排行榜、分享动态） | 与"零评判"定位冲突 |
| X-13 | 未成年用户 | 只面向 60+ 被记录者与成年子女 |
| X-14 | 数据出境 | ASR 与存储必须境内；见 9.2.3 |
| X-15 | 商业化（付费、广告、数据变现） | 一期不做；数据绝不出售或用于训练第三方模型 |

### 1.6 竞品与替代方案分析

**先说一个容易被忽略的事实：这个产品真正的替代方案不是别的 App，而是"什么都不做"和"家属自己的直觉判断"。** 大部分目标用户目前就是这么处理的。

| 类别 | 代表 | 做法 | 优点 | 缺陷 | 我们的差异 |
|---|---|---|---|---|---|
| **专业量表** | MoCA / MMSE / AD8 自评 | 在医院或线上做一次 10–30 分钟问卷 | 有临床依据、结果可解释 | 需要专门抽时间、老人抵触、**只反映"当天"状态** | 我们做的是**纵向、被动、零负担**的补充 |
| **认知训练 App** | Lumosity、脑力达人类 | 玩游戏测反应速度 / 记忆力 | 有趣、留存好 | **训练成绩 ≠ 日常能力**，本质是"考试式" | 我们不训练、不考试，只记录自然说话 |
| **医院随访系统** | 记忆门诊 / 脑健康中心 | 医生定期访谈 + 量表 | 金标准 | 一年一两次，**间隔太长**，中间的变化全丢失 | 我们做**高频日常**，补上两次门诊之间的空档 |
| **可穿戴 / 睡眠监测** | 手环、睡眠垫 | 步数、睡眠、心率 | 无感、可长期 | 与认知的关联弱，**解释不了** | 语言是认知最直接的窗口 |
| **学术语音筛查工具** | ADReSS 类研究原型 | 单次录音 + 模型判别 | 有论文支撑 | **只有一次结果，没有趋势**；直接给结论会触碰医疗器械红线 | 我们只做个人纵向比较，**不输出结论** |
| **替代方案：什么都不做** | — | 家属凭感觉观察 | 零成本 | 回忆偏差极大，往往"出事了才回头看" | 我们要证明"记录本身就有价值"（UR-06） |

**三条结论：**

1. **真正要争取的不是竞品用户，是"还没意识到要记录"的用户。** 所以产品第一层价值必须是**陪伴记录**，不能一上来就卖"筛查"——否则既抢不过医院，又触碰合规。
2. **"单次判别"这条路已经被学术工具占满，而且撞医疗器械红线。** 我们的护城河是**个人纵向趋势 + 家庭协作 + 就医衔接**这三件事的组合，竞品都没有同时做到。
3. **"认知训练 App"是错误的对标对象。** 它们卖的是"变好"，我们卖的是"看清楚"，产品语言、文案语气、甚至颜色系统都完全不同。做需求评审时如果有人拿脑力游戏来对标，要立刻纠正。

## 2. 利益相关者、用户角色与权限模型

### 2.1 角色表

| 角色 | 是谁 | 会不会用手机 | 核心诉求 | 恐惧 | 在产品里的位置 |
|---|---|---|---|---|---|
| **被记录者（老人）** | 60–85 岁，独居或与子女分居 | 不熟练、怕点错、看不清 | 不麻烦别人、留点声音给家人 | 被当成病人、被监视 | **老人端**：只有 1 个大按钮，零指标零趋势 |
| **照护者（子女）** | 30–55 岁，异地或同城 | 熟练 | 想知道"是不是真的在退化"、想有依据去看医生 | 看不出来、被误报吓到 | **家属端**：完整分析视图，独立账号远程查看 |
| **医生（间接）** | 神经内科 / 记忆门诊 | — | 想看到长期、结构化的变化记录 | 拿到一堆无用的手机截图 | 通过**就诊摘要导出**间接参与，不登录系统 |
| **研究者（项目负责人）** | 计算机专业 | 熟练 | 拿到可标注、可复现的语音数据 | 数据质量差、没有金标准 | **研究模式**：量表录入 + 数据导出 |
| **伦理/法务（间接）** | 单位 IRB、应用商店、监管 | — | 知情同意、数据最小化 | 医疗器械越界、敏感信息违规 | 约束条件来源（云端方案下权重更高） |

### 2.2 关键用户心理（直接决定交互设计）

1. **老人怕被"检查"** → 录音界面不能有倒计时压力、不能有评分、不能有红叉；失败也要给正向反馈
2. **老人怕麻烦子女** → 录音流程 ≤3 步，可一句话完成
3. **子女怕"看不出来"** → 家属端必须一眼回答"这周正常吗"
4. **子女怕误报** → 提示分级必须克制，**宁可漏报，不可误报**（一次误报即永久流失）
5. **用户怕隐私泄露** → 云端方案下这一点从"产品卖点"变成"合规义务"，必须在首次引导里讲清楚

### 2.3 用户画像（Persona）

角色表只是分类，真正做界面设计时要对着具体的人。下面四个画像中，**P1 和 P2 是必须同时满足的一对**——这也是本产品最难的地方：一个人觉得"这没什么用"，另一个人觉得"这是救命的东西"，而他们共用同一台手机。

---

**P1 张慧敏 · 42 岁 · 上海 · 主要使用者与付费决策人**

- 互联网公司中层，父母在安徽老家，一年回去 3–4 次
- 手机重度用户，每周给父母打 2–3 次电话，习惯用微信
- **触发她下载 App 的那一刻**：一次电话里，妈妈把同一个问题问了三遍
- 她最想要：一个"客观的东西"，来确认自己的担心是不是多虑
- 她最怕：**误报**。如果 App 提示有问题、医院却说没事，她会觉得自己被耍了，然后卸载
- 典型行为：会截图发到家庭群里跟兄弟姐妹商量；会拿给医生看
- **对设计的硬约束**：
  - 首页必须**一眼可读**，她通常是在通勤路上、睡前刷一眼
  - 必须能**一键生成可分享的材料**（她一定会发到家庭群）
  - 提示必须克制，一次误报 = 永久流失

---

**P2 王秀兰 · 78 岁 · 安徽 · 被记录者（核心）**

- 小学文化，主力是老年机，会用微信视频，但不会发朋友圈
- 听力略有下降，需要大字号 + 语音提示
- 说话带浓重方言口音
- 她的态度：**"录这个干嘛，我又没病"**
- 她真正在意的：不给儿女添麻烦
- **对设计的硬约束**：
  - 不能出现"评估""测试""检查""筛查"这类词
  - 必须能用一句话说清"这是留给家里人的"
  - **录音失败不能出现任何错误提示**（她会以为是自己弄坏了手机，然后不敢再用）
  - 不要让她看到任何数字、任何趋势、任何颜色警告

---

**P3 张建国 · 79 岁 · 与女儿同住 · 已诊断 MCI（次要但重要）**

- 已被诊断为 MCI，女儿希望长期跟踪变化
- 本人知道自己的情况，配合度高，**会主动想看趋势**
- 与 P2 恰好相反
- **对设计的硬约束**：老人端需要一个"我知情、我想看"的开关（**默认关闭**，但允许本人开启）。这一条不能因为 P2 的存在就砍掉。

---

**P4 李医生 · 记忆门诊 · 间接用户（决定「就诊摘要」的形态）**

- 每天看 30+ 个病人，平均问诊时间 8 分钟
- 最怕家属拿着一堆零散截图说"医生你看这个"
- 他想要：**一页纸**，有时间轴、有变化趋势、有事件和用药记录
- **对设计的硬约束**：「就诊摘要」必须是 **1–2 页、可打印、结构化**的，不是长图堆砌。内容顺序按医生阅读习惯排：基本信息 → 主诉 → 记录完成度 → 指标趋势 → 事件 → 家属观察 → 想问的问题

> ⚠️ 上述 Persona 目前**基于经验推演**，尚未做真实访谈。若项目需要写进论文或开题报告，应先补 5 位目标用户（3 子女 + 2 老人）的半结构化访谈。见 `planning/待确认事项.md` A1。

### 2.4 权限模型

**授权来源三种，全部由服务端强制校验，前端路由与按钮控制只用于体验：**

1. **身份（Identity）** —— 账号本身具备的角色
2. **绑定关系（Binding）** —— 家属与被记录者之间的授权，可撤销
3. **知情同意（Consent）** —— 研究模式下对研究者的授权，可单独撤回

**角色码**

| 角色码 | 含义 | 授权来源 |
|---|---|---|
| `ELDER` | 被记录者本人 | 身份 |
| `CAREGIVER_READONLY` | 只读家属 | 绑定关系 |
| `CAREGIVER_EDITOR` | 可编辑家属 | 绑定关系 |
| `RESEARCHER` | 研究者 | 研究知情同意 |
| `OPS_ADMIN` | 运营管理员 | 身份；**不得访问任何音频与转写内容** |
| `SYSTEM` | 内部服务身份 | 服务凭证 |

**权限矩阵**

| 资源 | ELDER | CG_READONLY | CG_EDITOR | RESEARCHER | OPS_ADMIN |
|---|---|---|---|---|---|
| 音频文件 | 读 / 删 | 读 | 读 | 匿名读（需研究同意） | **禁止** |
| 声学与文本指标 | 读（需本人开启查看开关，默认关） | 读 | 读 | 匿名读 | 禁止 |
| ASR 转写文本 | 读 | 读 | 读 / 改 | 匿名读 | **禁止** |
| 人工校订文本 | — | — | — | 读 / 写 | 禁止 |
| 事件标注与备注 | 读 | 读 | 读 / 写 / 删 | 匿名读 | 禁止 |
| 就诊摘要 | 读 | 生成 / 导出 | 生成 / 导出 | 禁止 | 禁止 |
| 临床量表 | — | **禁止** | **禁止** | 读 / 写 | 禁止 |
| 账号资料 | 读 / 改 | 读 / 改自己 | 读 / 改自己 | 读 / 改自己 | 读（不含音频与文本） |
| 研究数据集导出 | — | — | — | 导出 | 禁止 |

**四条硬规则**

1. **越权一律返回 404，不返回 403。** 避免通过错误码探测资源是否存在（防 IDOR 枚举）。
2. **家属的访问权随绑定解除即时失效**，包括已生成但未过期的签名 URL。
3. **研究者只能看到匿名 ID**，界面与导出文件中均不出现真实姓名。
4. **运营管理员在数据层就没有音频读权限**，不是靠界面隐藏。

### 2.5 资源归属规则

| 资源 | 归属主体 | 说明 |
|---|---|---|
| 音频、记录、指标、转写 | **被记录者（subjectId）** | 归属数据主体本人，**不归属上传者** |
| 家属备注与事件标注 | 标注者（caregiverId） | 家属自己写的内容归自己，但被记录者可见 |
| 临床量表 | 被记录者 + 研究项目 | 仅研究模式下存在 |
| 就诊摘要文件 | 生成者（caregiverId） | 本地文件，不上云 |

**由此推出的三条业务规则**

1. **家属代录（UC-09）产生的记录，归属仍是被记录者**，但必须写入 `recorderRole = CAREGIVER` 字段。论文取数时须区分代录样本。
2. **删除权归被记录者本人。** 家属不能单方面删除老人的记录——这是伦理要求，不只是合规要求。
3. **代录与代删需要被记录者的授权。** 一期通过"同机模式二次确认"实现；远程代删不支持。

> ⚠️ 若被记录者已丧失民事行为能力、由家属作为监护人，上述第 2、3 条需按监护关系调整。这是一个**法律判断**，不是产品判断，需法务出书面意见。见 `planning/待确认事项.md` C1。

### 3.2 使用场景

**场景 1｜老人日常录音（每日 1 次，60 秒内完成）**
- 前置：App 已装好，老人已学会"点大圆按钮"
- 流程：打开 → 看到话题卡 → 点"开始说话" → 说 40 秒 → 点"说完了" → 显示"今天记好了，谢谢您"
- 异常：断网 → 录音照常完成，本地排队待上传；麦克风被占用 → 提示"等一下再试试"；录音中断 → 自动保存已录部分
- 成功标准：老人独立完成率 ≥60%，单次耗时 ≤60 秒，**断网时功能不降级**

**场景 2｜云端分析**
- 前置：录音完成
- 流程：声学指标本地即时算完（省服务端算力）→ 音频上传 → 云端 ASR → 文本指标 → 结果回写本地缓存与云端
- 异常：上传失败 → 指数退避重试；ASR 失败 → 该条只保留声学指标，标记"文本分析未完成"
- 成功标准：联网状态下，从录音结束到指标可见 ≤60 秒

**场景 3｜家属远程查看（核心场景）**
- 前置：子女已绑定老人账号
- 流程：子女在自己手机上打开家属端 → 直接看到老人最新的记录与趋势（无需老人操作任何事）
- 异常：老人手机断网多日 → 家属端显示"最近一次同步：3 天前"，并说明数据可能滞后
- 成功标准：老人录完 1 分钟内，子女端可见

**场景 4｜出现持续变化**
- 流程：家属端首页出现橙色卡片（"近两周 3 次记录中说话速度比平时慢一些，也可能只是累了"）→ 点击看趋势详情 → 若持续 4 周升级为"建议安排一次专业评估" → 一键生成就诊摘要
- 成功标准：从提示到生成就诊摘要 ≤3 次点击

**场景 5｜老人忘记录**
- 流程：到设定时间老人端弹温和提醒；连续 3 天未录 → 自动降频（隔天提醒），不追加压力；家属端同时收到提示，可远程"帮他录"
- 成功标准：提醒不引起反感，依从率 ≥70%

**场景 6｜研究采集（可选）**
- 流程：研究模式 → 按协议提示每周完成图片描述任务 → 录入 MoCA-B/MMSE 分数 → 导出全部原始数据（音频 + ASR 文本 + 指标 CSV + 量表）
- 云端方案优势：支持远程受试者、多中心采集、集中标注

| FR-9.3 | 权限最小化：麦克风 + 通知 + 网络 | M | 不申请通讯录、定位、相册等无关权限 |
| FR-9.4 | 账号登录与多设备会话管理 | M | 老人端登录态长期有效，不频繁掉线 |

### 4.11 需求与论文的映射

| 需求模块 | 服务产品 | 服务论文 | 说明 |
|---|---|---|---|
| FR-1 录音采集 | ✅ 核心 | ✅（若走路径 2） | 采集协议要与论文任务范式一致 |

| FR-5 家属端 | ✅ 核心 | ❌ | 纯产品需求 |

## 5. 业务规则与状态流转

### 5.1 状态机 S0–S6

| 状态 | 触发条件（建议，需算法定稿） | 表现 | 文案模板 |
|---|---|---|---|
| S0 未开始 | 0 条有效记录 | 灰 | "先录第一条吧，第一次只是给爸爸建立他自己的基准。" |
| S1 基线建立中 | 1–3 条 | 灰 + 进度 | "还需要 2 次记录，才能开始看趋势。" |
| S2 稳定 | ≥4 条且无越界 | 绿 | "本周的语言表达和平时差不多。" |
| S3 数据不足/波动 | 有效记录 <4 条或仅单项轻度偏离 | 灰蓝 | "这周记录少了点，趋势先不下结论。" |
| S4 需要关注 | 连续 3 次（或 2 周内 3 次）≥1 项核心指标低于基线 1.5SD | 橙 | "近两周有 3 次记录里说话速度比平时慢一些。这可能只是累了，也可能是最近说话变少。建议继续记录并留意他的日常状态。" |
| S5 建议就医评估 | 连续 4 周多指标同向下降 | 深橙（**不用红**） | "近 4 周的语言表达变化比较持续。可以和家人商量，带他去做一次专业的记忆或认知评估——这不代表有问题，只是做个确认更安心。" |
| S6 已就医/已处理 | 家属手动标记 | 灰绿 | "已记录：2026-10-15 已就诊。继续记录有助于医生看长期变化。" |

**设计原则**：升级缓慢、降级自动、不用红色、必带非疾病解释、老人端永远不显示异常状态。

**状态流转规则**

| 规则 | 内容 |
|---|---|
| 升级需连续证据 | S2 → S4 需连续 3 次；S4 → S5 需连续 4 周 |
| 降级自动 | 回到基线范围后自动降级，不保留"历史最高状态" |
| 数据不足强制降级 | 有效记录 <4 条时一律回落到 S3，不保留 S4/S5 |
| 状态只在服务端计算 | 前端只渲染 `statusCode`，不自行判断 |
| 状态与文案解耦 | 服务端返回文案 key，前端渲染；见 `api/00-接口通则.md` |

### 5.2 指标字典（前端 × 算法契约）

| 维度 | 算法指标 | 前端展示名 | 模态来源 | 家属看得懂的解释 | 陷阱 |
|---|---|---|---|---|---|
| 语速 | 字/分钟、音节率、发音速率 | 说话速度 | 声学 | "平时 1 分钟约说 180 个字，本周平均 150 个。" | 受话题内容影响大，必须同任务类型内比较 |
| 停顿 | 平均停顿时长、>2s 长停顿次数、停顿占比、语流比 | 说话流畅度 | 声学 | "说话中间停下来的次数比平时多了一些。" | 感冒、鼻塞、嘈杂环境影响大 |
| 用词丰富度 | TTR、MATTR、罕见词比例、实词/虚词比 | 用词丰富程度 | 文本 | "这周用的不一样的词比平时少了一点。" | 短样本 TTR 极不稳，**必须用 MATTR**；ASR 错字会污染该指标 |
| 句子连贯性 | 平均句长、从句密度、连接词率、语义连贯/话题漂移、命题密度 | 说话的连贯性 | 文本 | "句子的连接比平时松了一些，说到后面容易换话题。" | 与 ASR 质量强相关，必须报告 ASR 置信度 |

**前端呈现 5 条硬规则**

1. 不显示原始数值，只显示趋势方向与状态标签
2. 必须显示数据充分度（有效记录 <4 条 → 全部标"数据不足，仅供参考"）
3. 基线统一定义：前 14 天或前 4 次有效记录，之后 28 天滚动更新；需显示"基线建立中（还差 N 次）"
4. 每个指标配固定白话解释，点击"这是什么"展开
5. 任何"变化"标签旁必须并列非疾病解释

### 5.3 质量门控规则

| 条件 | 判定 | 处理 |
|---|---|---|
| 时长 <10 秒 | 无效 | 静默丢弃，不提示失败 |
| 时长 10–15 秒 | 存疑 | 保留但不计入趋势 |
| SNR 低于阈值 | 无效 | 保留 + 标记，不计入趋势 |
| 静音占比 >70% | 无效 | 同上 |
| ASR 置信度低于阈值 | 部分有效 | 保留声学指标；文本指标置 `null` |
| 同任务类型有效记录 <4 条 | 数据不足 | 状态强制回落 S3 |

**关键约束：不合格记录**保留但不参与趋势计算**。** 用户不应因为"白录了"而失去记录（UR-06），但也不能让噪声污染基线。

### 5.4 文案与禁用词规则

**禁用词表（前端做代码级校验，命中即构建失败）**

诊断、确诊、患病、风险预测、概率、筛查、异常、恶化、衰退、痴呆、阿尔茨海默、病变、评分、得分、不合格、**MMSE**、**MoCA**（后两者仅研究模式可见）

**文案规范**

- 家属端用第二人称对子女说话，第三人称指老人
- 句子 ≤25 字，不直接出现术语
- 数据不足时主动承认："记录还太少，先不下结论"
- 所有提示都带退路："可能只是累了 / 可以继续观察 / 不代表有问题"
- 老人端文案必须可 TTS 朗读
- 完整文案表见 `frontend/原型设计说明书.md` 附录 A

### 5.5 采集协议（产品轨 + 研究轨）

| 轨道 | 频率 | 时长 | 任务 | 用途 |
|---|---|---|---|---|
| 产品轨（每日） | 每天 1 次 | 30–60 秒 | 自由叙述"今天发生了什么" | 依从性 + 趋势 |
| 研究轨（每周） | 每周 1 次 | 约 3 分钟 | 图片描述 60s + 语义流畅性 60s + 自由叙述 60s | 与 MoCA 做效度验证 |

采样窗口固定（如 19:00–21:00），**但必须记录实际时间戳**（研究显示老年人 EMA 晚间依从率低于早间，时间本身是协变量）。

> 关于"每天录 vs 每周录"的完整论证：结论是**嵌套设计**，被迫二选一时选日频（分析单元是"人"不是"录音"，12 周日频 84 点 vs 周频 12 点）。但**注意**：这个结论只在你走"路径 2（自建数据集）"时才影响论文；如果论文用公开数据集（路径 3），采集频率只影响产品体验。

## 7. 数据对象与生命周期

### 7.1 数据对象清单

|---|---|---|---|
| `Account` 账号（家属） | 本人 | 一般个人信息 | 账号名、邮箱、密码哈希、性别（儿子/女儿派生） |

| `AudioObject` 音频对象 | 被记录者 | **敏感（含生物识别特征）** | 对象存储中的二进制 |
| `Transcript` 转写文本 | 被记录者 | **敏感（医疗健康）** | ASR 文本 + 人工校订文本 |
| `Metric` 指标 | 被记录者 | **敏感（医疗健康）** | 声学 + 文本指标 |
| `Baseline` 基线 | 被记录者 | **敏感（医疗健康）** | 均值、标准差、样本数 |
| `StatusSnapshot` 状态快照 | 被记录者 | **敏感（医疗健康）** | S0–S6 历史 |
| `EventTag` 事件标注 | 家属 | 敏感（医疗健康） | 感冒/搬家/住院 |
| `Consent` 知情同意 | 本人 | 敏感 | 产品同意 + 敏感信息单独同意 + 研究同意 |
| `ClinicalScale` 临床量表 | 被记录者 | **敏感（医疗健康）** | 仅研究模式 |
| `AuditLog` 审计日志 | 系统 | 一般 | 谁在何时读了哪条音频 |

### 7.2 核心数据字段

```
subjectId, recorderRole(ELDER/CAREGIVER), recordId
taskType(DAILY_FREE | WEEKLY_PICTURE | WEEKLY_FLUENCY | WEEKLY_FREE)
scheduledAt, actualStartedAt, durationSec, sampleRate, snrDb
asrText, asrTextManual(人工校订), asrConfidence, dialect, qualityFlag

```

### 7.3 保留期限与自动清理

| 数据 | 默认保留 | 可调 | 到期行为 |
|---|---|---|---|
| 音频文件 | 24 个月 | 是（6 / 12 / 24 / 永久） | 硬删除 + 对象存储生命周期规则兜底 |
| 转写文本与指标 | 与音频同期 | 否 | 随音频一并删除 |
| 基线数据 | 持续更新 | 否 | 随账号存在 |
| 状态快照 | 24 个月 | 否 | 硬删除 |
| 审计日志 | 12 个月 | 否 | 硬删除 |
| 临床量表 | 研究项目存续期 | 否 | 研究项目结束时按伦理承诺处理 |

**规则**

1. 保留期限必须在隐私政策中写明**具体天数**，不能写"合理期限"
2. 用户可在 P-F7 调整自己的留存期限
3. 到期清理必须是**硬删除**（含对象存储副本与备份中的副本，备份副本按备份轮转周期自然过期，需在隐私政策中说明）

### 7.4 删除与注销

| 操作 | 触发 | 范围 | 确认 |
|---|---|---|---|
| 删除单条记录 | 被记录者或 `CG_EDITOR` | 音频 + 转写 + 指标 + 该条事件标注 | 二次确认 |
| 清空全部记录 | **仅被记录者** | 该 subjectId 下全部记录，保留账号 | 二次确认 + 输入确认词 |
| 注销账号 | 本人 | 账号 + 全部关联数据，**不可恢复** | 二次确认 + 输入确认词 + 7 天冷静期 |
| 撤回研究同意 | 本人 | 停止研究使用；已导出的匿名数据集按伦理承诺处理 | 说明不可追溯部分 |
| 撤回敏感信息同意 | 本人 | 服务降级为不可用（因为录音本身就是敏感信息），需明确告知 | 二次确认 |

**硬规则**

1. 删除必须**同步到云端**，不能只删本地
2. 删除操作必须写入审计日志（记录操作者、时间、对象，不记录内容）
3. 注销后不得保留任何可用于识别个人的数据；匿名化统计可保留
4. **不得用"账号注销"作为留存的挡箭牌**——注销即彻底删除

## 8. 非功能需求（NFR）

### 8.1 NFR-1 安全与隐私

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-1.1 | 全链路加密：传输 TLS 1.2+、音频对象存储服务端加密、数据库字段级加密 | 语音属敏感个人信息 |
| NFR-1.2 | 本地缓存用 SQLCipher / EncryptedFile 加密 | 断网兜底数据也要保护 |
| NFR-1.3 | **敏感个人信息单独同意**，与用户协议分离，可单独撤回 | 《个人信息保护法》要求 |
| NFR-1.4 | 不采集声纹、不做身份识别 | 生物特征类数据一律不碰 |
| NFR-1.5 | 数据留存期限约定 + 到期自动删除 + 注销即彻底删除 | 见 7.3 / 7.4 |
| NFR-1.6 | **ASR 与存储使用境内服务**，禁止数据出境 | 若必须出境需做安全评估与备案 |
| NFR-1.7 | 访问审计日志：谁在什么时间读了哪条音频 | 云端可追溯性要求 |
| NFR-1.8 | 家属协作需明确权限（只读/可编辑）与操作日志 | 见 2.4 |

### 8.2 NFR-2 性能

| 编号 | 指标 | 目标 |
|---|---|---|
| NFR-2.1 | 录音启动延迟 | ≤1 秒（含麦克风预热） |
| NFR-2.2 | 声学指标计算（本地） | 录音结束后 ≤5 秒 |
| NFR-2.3 | 云端 ASR 返回（含上传） | 1 分钟音频 ≤30 秒 |
| NFR-2.4 | 首屏渲染 | ≤2 秒 |
| NFR-2.5 | **APK 体积** | ≤40MB（ASR 在云端，无需打包模型） |
| NFR-2.6 | 弱网/断网表现 | 录音不降级；上传失败静默重试，不弹错误 |
| NFR-2.7 | 长时间录音（5 分钟）不卡顿 | 波形用 Canvas/自定义绘制，避免逐帧重绘 |

### 8.3 NFR-3 可用性

| 编号 | 需求 |
|---|---|
| NFR-3.1 | 老人端录音流程 ≤3 步，单次 ≤60 秒 |
| NFR-3.2 | 首次引导 ≤6 步完成 |
| NFR-3.3 | 任何网络/权限异常都有明确的用户可理解文案，不使用错误码 |
| NFR-3.4 | 老人端登录态长期有效（≥90 天），不频繁掉线 |
| NFR-3.5 | 提示语全部可被 TTS 朗读 |

### 8.4 NFR-4 无障碍与适老（老人端硬指标）

- 正文 ≥18sp，按钮文字 ≥20sp；提供三档字号
- 对比度 ≥4.5:1；点击区 ≥48dp（录音按钮 ≥120dp）
- 全流程单手可操作，主操作按钮位于屏幕下半区
- 关键操作配语音提示（TTS）；支持系统"减少动态效果"
- 老人端**无二级菜单**、无滑动切换
- 遵循 WCAG 2.2 AA 核心要求（对比度、焦点可见、目标尺寸、错误可识别）

### 8.5 NFR-5 兼容性

- Android 8.0（API 26）及以上；适配刘海屏、折叠屏
- 主流国产 ROM（MIUI / HarmonyOS / ColorOS / OriginOS）的后台限制与自启管理需处理（**尤其影响上传与提醒**）
- 方言识别降级策略：识别质量低时不影响录音与声学指标

### 8.6 NFR-6 可观测性

| 编号 | 需求 |
|---|---|
| NFR-6.1 | 客户端崩溃与 ANR 上报（不含音频与转写内容） |
| NFR-6.2 | 服务端结构化日志：请求 ID、耗时、错误码、状态流转 |
| NFR-6.3 | 关键业务指标：上传成功率、ASR 成功率与耗时、同步延迟、状态升级次数 |
| NFR-6.4 | 告警：ASR 失败率、上传失败率、队列积压超过阈值 |
| NFR-6.5 | **日志与埋点不得记录音频、转写全文、手机号明文、令牌、密钥** |

### 8.7 NFR-7 可靠性与可维护性

- 音频**永不丢失**：写入即落盘，先本地队列再上传
- 分析引擎与数据源均接口化：论文算法、后端实现均可整体替换而不动 UI
- 数据库需支持版本迁移（论文迭代会反复改指标字段）
- 关键路径幂等：重复上传、重复触发分析不得产生重复记录

## 9. 安全、隐私、日志与审计

### 9.1 安全控制清单（对照 OWASP Top 10 / ASVS）

| # | 风险 | 控制措施 | 验证方式 |
|---|---|---|---|
| 1 | 访问控制失效 / IDOR | 服务端强制鉴权 + 资源归属校验；越权返回 404 | 越权测试用例 |
| 2 | 加密失败 | TLS 1.2+；对象存储 SSE；字段级加密；本地 SQLCipher | 配置核查 + 抓包 |
| 3 | 注入 | 全部走 ORM / 参数化查询，**禁止字符串拼接 SQL** | 代码审查 + 静态扫描 |
| 4 | 不安全设计 | 权限矩阵前置设计（2.4）；默认拒绝 | 设计评审 |
| 5 | 安全配置错误 | 安全响应头；关闭调试端点；最小权限凭证 | 部署核查 |
| 6 | 组件与供应链 | 采用前查官方文档、维护状态、许可证、CVE | 依赖清单审查 |
| 7 | 认证失败 | 验证码 + 令牌；令牌短时效 + 刷新；登录限流 | 认证测试 |
| 8 | 数据完整性 | 上传校验和；指标写入幂等 | 集成测试 |
| 9 | 日志与监控不足 | 审计日志 + 告警（8.6） | 告警演练 |
| 10 | SSRF | 预签名 URL 域名白名单，禁止用户可控 URL | 安全测试 |

**通用要求**

- 密码必须 Argon2id 或 bcrypt 哈希存储（2026-09-28 起：邮箱注册 + 密码登录，验证码仅用于注册与忘记密码）
- 会话：令牌存于安全存储，不使用明文 SharedPreferences
- CSRF：接口使用 Bearer 令牌而非 Cookie，天然规避；若引入 Cookie 必须加 SameSite + CSRF Token
- 输出：DTO 白名单字段，敏感字段脱敏（邮箱本地段打码，如 `use***@qq.com`）
- 富文本：本项目**不渲染任何用户输入的 HTML**，一律按纯文本转义

### 9.2 隐私与合规

#### 9.2.1 法律依据与义务

| 事项 | 依据 | 落实 |
|---|---|---|
| 敏感个人信息处理 | 《个人信息保护法》第 28–29 条 | 单独同意 + 告知必要性与影响 |
| 个人信息保护影响评估 | 同法第 55 条 | 上线前完成 PIA 并留档 |
| 数据出境 | 同法第 38–40 条 | **境内 ASR 与存储**，从源头规避 |
| 最小必要 | 同法第 6 条 | 权限最小化（FR-9.3）+ 字段最小化 |
| 第三方个人信息 | 同法第 13、23 条 | 家属录老人语音需老人知情同意，见 9.2.2 |

> 以上为产品侧合规要求，**具体法律条文与结论需法务复核**，本文档不作为法律意见。

#### 9.2.2 第三方个人信息（本项目特有风险）

家属录制老人的语音，属于**处理第三方（老人）的个人敏感信息**。这既是法律风险也是伦理风险——子女的关心可能正是父母抗拒的"被监测"。

**必须做到**

1. 首次引导中的"老人知情"必须是**独立一步**，不能藏在长条款里（P-O2）
2. 老人版知情同意必须**大字 + 可语音朗读**
3. 老人端必须有一个**随时可见、可撤回**的同意状态入口（P-E4）
4. 撤回后：停止采集，已采集数据按老人意愿删除或保留

#### 9.2.3 数据出境

- ASR 与对象存储**必须使用境内服务**（建议讯飞 / 阿里云 / 腾讯云）
- 禁止使用境外 ASR API（OpenAI Whisper API、Google STT、Azure Speech 等）
- 若未来必须出境，需先完成安全评估与备案，并更新隐私政策

#### 9.2.4 就诊摘要边界（最容易越界的功能）

**问题**：把"语速下降 15%"这类**非临床指标**结构化后递给医生，会落入《医疗器械分类目录》21-04「决策支持软件」的定义（"给出临床诊断治疗依据和/或建议"），从而被按第三类医疗器械管理。

**允许**：导出原始录音 + 家属自己写的观察 + 事件时间轴 + 记录完成度。
**禁止**：生成任何面向医生的结构化临床判断、风险分级、指标解读、检查建议。

**一句话判据**：**App 只搬运数据，不做解读。解读是医生的事。**

> 完整合规风险分析（四层风险、文案红线光谱、三条底线）见 `planning/合规风险备忘.md`。

### 9.3 日志与审计

| 类型 | 记录内容 | 禁止记录 |
|---|---|---|
| 访问审计 | 操作者 ID、角色、时间、资源 ID、操作类型、来源 IP | 音频内容、转写全文 |
| 业务日志 | 请求 ID、接口、耗时、状态码、状态流转 | 手机号明文、令牌、Cookie、密钥 |
| 错误日志 | 异常类型、堆栈（脱敏）、请求 ID | 请求体原文（可能含转写） |

**审计要求**：音频读取必须留痕；审计日志保留 12 个月；日志不可被业务代码修改。

### 9.4 密钥管理

1. 真实密钥只存在于环境变量或密钥托管服务，**绝不进仓库**
2. `.env.example` 只放占位符，不含真实值
3. 前端构建产物**不得包含任何服务端密钥**（ASR、对象存储、数据库凭证一律不下发客户端）
4. 客户端需要的敏感能力（如 ASR）**全部通过后端代理**，客户端不直连第三方
5. 预签名 URL 短时效（建议 ≤15 分钟），且绑定单一对象

### 9.5 文件上传安全（音频）

| 要求 | 落实 |
|---|---|
| 扩展名 / MIME / 文件签名联合校验 | 三者一致才接受，不信任客户端声明 |
| 大小与数量限制 | 单文件 ≤10MB；单用户日上传条数上限 |
| 配额 | 按账号设置存储配额，超限拒绝并提示 |
| 随机对象键 | `{subjectId}/{yyyy}/{mm}/{uuid}.m4a`，不可预测 |
| 私有存储 | 对象默认私有，仅通过短期签名 URL 访问 |
| 异步处理 | 上传后异步触发分析，不在请求内做重活 |
| 内容安全 | 只接受音频容器格式；**不执行用户上传的任何脚本、宏、可执行文件** |
| 校验和 | 上传携带 SHA-256，服务端校验，防篡改与重复 |

录音漏斗（进入→开始→完成）、时长分布、重录率、放弃时长与时段、话题卡点击率、提醒送达→录音转化率、趋势页停留、事件标注使用率、状态升级→就诊摘要下载→实际就医回填、**上传成功率与同步延迟**（云端方案下最关键的技术指标）

## 10. API 原则

完整规范见 **`api/00-接口通则.md`**，业务接口见 `api/API-01` 至 `API-06`。本节只列总原则。

| # | 原则 |
|---|---|
| 1 | **`api/` 是前后端唯一接口事实来源**，禁止前后端各自维护一套 |
| 2 | 服务端返回**文案 key** 而不是整句文案 —— 状态机文案由前端渲染，改文案不发版 |
| 3 | 指标一律返回原始数值（`Float?`），前端负责"不显示数值、只显示趋势与状态"的呈现规则 |
| 4 | 所有时间用**毫秒时间戳**，不用字符串日期 |
| 5 | 任何可能为空的字段都显式可为空 —— 声学指标永远有，文本指标在 ASR 失败时为 `null` |
| 6 | 音频**不上传业务服务器**，走预签名 URL 直传对象存储 |
| 7 | 写操作幂等：上传与分析触发均需 `Idempotency-Key` |
| 8 | 列表接口统一分页（游标分页，避免深分页）；排序、过滤走统一查询参数 |
| 9 | 版本走 URL 前缀 `/v1`；破坏性变更升版本，不原地改语义 |
| 10 | 错误统一结构 `{ code, message, requestId, details? }`，`code` 为稳定枚举，`message` 面向用户可本地化 |
| 11 | 限流按 IP + 账号 + 接口三维，高风险接口更严 |
| 12 | 越权返回 404 而非 403 |

## 13. 里程碑与分期

### 13.1 MVP 定义

**MVP = 能连续采集 4 周、指标不出错、趋势图正确、断网不丢数据。** 后端可先用 Mock。

MVP 不含：家属远程绑定、多家属协作、研究模式、就诊摘要。

### 13.2 分期

| 阶段 | 目标 | 包含需求 | 完成标准 |
|---|---|---|---|
| **P0 可跑通** | 验证"录音→分析→趋势"链路 | FR-1.1–1.4、FR-2.1–2.5、FR-3.1–3.3、FR-4.1–4.3、FR-5.2–5.3、FR-6.1–6.2、FR-9.1–9.3 | 能连续采集 4 周，指标不出错，趋势图正确（**后端可先 Mock**） |
| **P1 论文可用** | 支撑数据采集与实验 | +FR-1.6、FR-8.1–8.6 | 能导出符合论文数据字典的完整数据集 |
| **P2 产品可用** | 家属端完整闭环 | +FR-5.1、FR-5.4、FR-5.7、FR-6.3–6.6、FR-4.4、FR-7.1–7.2、FR-9.4 | 依从率 ≥70%，家属远程可见，断网不丢数据 |
| **P3 增强** | 体验与科研扩展 | +FR-1.5、FR-1.7、FR-3.4、FR-5.5–5.6、FR-7.3、FR-8.7 | 多家属协作、同机切换 |

### 13.3 里程碑与关键路径

| 里程碑 | 内容 | 阻塞项 |
|---|---|---|
| M0 | 规范文档冻结（本文档 + frontend + backend + api） | 待确认项 C1 / C2 |
| M1 | 前端 P0 可跑通（Mock 后端） | 无 |

## 14. 约束、假设与风险

### 14.1 硬约束

| 约束 | 内容 |
|---|---|
| 平台 | Android 原生（Kotlin + Jetpack Compose） |
| 存储 | **离线优先 + 云端同步**：本地 Room 缓存 + 云端真源 |
| 网络 | 需要 `INTERNET` 权限；**断网必须仍可完成录音** |
| 后端 | 需要服务端（账号 / 对象存储 / 分析队列 / ASR）；前端按 `api/` 契约开发 |
| 合规 | 不做诊断/筛查/概率/评分；禁用词表见 5.4；就诊摘要边界见 9.2.4 |
| 合规 | NMPA 2023 年分类界定中"认知功能障碍评估与治疗软件"被按**第三类医疗器械**管理 → 产品名与宣传语必须过法务 |
| 合规 | 语音为敏感个人信息：单独同意 + 全链路加密 + 访问审计 + 留存期限；ASR 用境内服务 |
| 合规 | 产品名「认知健康日记」本身含功能声称风险，见 15.1 |

### 14.2 假设

| # | 假设 | 若不成立的影响 |
|---|---|---|
| A1 | 老人手机为 Android，且系统版本 ≥8.0 | 需补 iOS，工作量翻倍 |
| A2 | 老人有能力学会"点一个大按钮" | 需要家属长期代录，依从性方案要重做 |
| A3 | 后端能按 `api/` 契约提供接口 | 前端只能用 Mock 演示，无法联调 |
| A4 | 老人端网络条件足以完成音频上传 | 需加强离线队列与延迟上传策略 |
| A5 | 论文用公开数据集完成实验，不需要 App 产出数据 | 若需要 App 数据，则必须补伦理批件 + 医院合作，周期 +6 个月 |
| A6 | 主要用户是老人本人使用（当前设计） | 若实际以子女代录为主，老人端设计分量需大幅下调，见 15.1 |

### 14.3 风险清单

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| R1 | **云端成本随用户量线性增长**（ASR + 存储 + 带宽） | 高 | 商业模式不成立 | 先测算单用户月度成本；音频设留存期限；只对有效录音调用 ASR |
| R2 | **敏感个人信息上云违规** | 中 | 行政处罚 + 品牌崩塌 | 境内服务、单独同意、全链路加密、留存期限、访问审计 |
| R3 | 后端进度拖住前端 | 高 | 前端无法联调、项目停摆 | 前端严格按 `api/` 契约 + Mock 开发，不等后端 |
| R4 | **被认定为医疗器械** | 中 | 无法上架/被罚 | 严守"记录+提示"定位；产品名与宣传语过法务；禁用词做代码级校验；就诊摘要守 9.2.4 边界 |
| R5 | 误报导致用户流失 | 中 | 致命 | 提示分级缓慢、必带非疾病解释、不用红色 |
| R6 | 老人抵触或学不会 | 高 | 数据量不足 | 家属代录、话题库轮换、老人端零指标、正向反馈 |
| R7 | 断网时录不了音 | 中 | 关键数据丢失 | 离线优先架构；录音先落本地、联网补传 |
| R8 | 短样本指标不稳，被审稿人质疑 | 中 | 论文被拒 | 补重测信度 ICC、质量门控、报告排除标准 |
| R9 | App 与论文互相拖累 | 中 | 两头做不好 | 严格按 4.11 分离：论文只在 FR-8，产品需求不阻塞论文实验 |
| R10 | ASR 文本与论文人工转录口径不一致 | 高 | 结论不可比 | 产品指标标"估算值"；研究模式双文本并存 |
| R11 | **假阴性导致延误就诊** | 中 | 伦理责任 | 全站不承诺"正常"；措辞永远保留"继续观察"；不输出"没问题"结论 |
| R12 | 产品名被判定为功能声称 | 中 | 需改名，品牌资产损失 | M0 阶段一并过法务，不要等到上架前 |

1. **任何需求变更必须回写本文档**，不允许只在聊天或计划文件里达成一致
2. 变更需记录：变更内容、原因、影响范围、受影响的下游文档、生效版本

4. **触及 `api/` 契约的变更**必须先改契约、再改实现；破坏性变更升 API 版本
5. 变更后必须同步更新：受影响的模块文档、验收清单（12.5）、风险清单（14.3）
6. 文档版本号规则：`主版本.次版本`。新增章节 → 次版本 +1；改变范围或推翻既有决策 → 主版本 +1
