# 模块：状态与提醒

**覆盖需求**：FR-4（状态与提醒）
**覆盖页面**：P-F1 状态横幅部分、P-F5 话题库与提醒
**路由**：`family/topics`；状态横幅内嵌于 `family/overview`

---

## 1. 模块职责与边界

### 1.1 职责

把服务端算出的状态机结果（S0–S6）**按合规文案渲染**给家属，并管理"什么时候温和地提醒老人录一次"。

### 1.2 明确不做

| 不做 | 理由 |
|---|---|
| **不在前端计算状态** | 状态只在服务端计算，前端只渲染 `statusCode` |
| **不硬编码状态文案** | 服务端返回文案 key，前端渲染；改文案不发版 |
| 不使用红色 | 全站红线 |
| 不使用"立即 / 尽快 / 危险 / 严重 / 警告" | 制造恐慌，且暗示医疗判断 |
| 不做升级的即时推送轰炸 | 升级必须缓慢，见 3.3 |
| 不做"未读红点" | 红色 + 焦虑感 |
| 不做连续打卡奖励、不做"坚持了 N 天"徽章 | 把记录变成任务，与"零压力"冲突 |

## 3. 状态机与渲染规则

### 3.1 七个状态

| 状态 | 表现色 | 文案要点 |
|---|---|---|
| S0 未开始 | 灰 | 引导录第一条 |
| S1 基线建立中 | 灰 + 进度 | 说明还差几次 |
| S2 稳定 | 绿 | "和平时差不多" |
| S3 数据不足/波动 | 灰蓝 | "先不下结论" |
| S4 需要关注 | 橙 | **必须并列非疾病解释** |
| S5 建议就医评估 | 深橙（**不用红**） | 提供明确行动按钮 |
| S6 已就医/已处理 | 灰绿 | 记录就诊，鼓励继续 |

完整文案见 `../原型设计说明书.md` 附录 A.3。

### 3.2 渲染契约

服务端返回（见 `../../api/API-03-指标与趋势.md`）：

```
{ statusCode: "S4", copyKey: "status.s4", validRecordCount: 3, ... }
```

前端职责：

1. `statusCode` → 表现色 + 竖条颜色
2. `copyKey` → 从 `ui/copy/` 取文案（**不拼接、不判断、不加工**）
3. `validRecordCount` → 传给 `SufficiencyBar`

**前端不做的**：不根据 `validRecordCount` 自行降级状态，不根据指标自行升级状态。**降级与升级逻辑全部在服务端。**

### 3.3 升级与降级（服务端规则，前端只呈现）

| 规则 | 内容 |
|---|---|
| 升级需连续证据 | S2 → S4 需连续 3 次；S4 → S5 需连续 4 周 |
| 降级自动 | 回到基线范围后自动降级，**不保留历史最高状态** |
| 数据不足强制降级 | 有效记录 <4 条一律回落 S3 |
| 状态只在服务端计算 | 前端无状态判定代码 |

**前端必须处理的一个边界**：状态从 S4 降到 S2 时，**不能出现"好转了/恢复了"这类措辞**——那等于在给健康结论。降级文案只描述当前状态，不描述方向。

### 3.4 非疾病解释（FR-4.3）

S4 及以上**必须**并列非疾病解释，且视觉比重 ≥1/3：

> "近两周有 3 次记录里说话速度比平时慢一些。**这可能只是累了，也可能是最近说话变少。**建议继续记录并留意他的日常状态。"

**组件级约束**：`StatusBanner` 在 `statusCode ∈ {S4, S5}` 时，若 `nonDiseaseExplanation` 为空，**渲染失败并抛出**（不是警告，是失败）。用机制保证这条红线不会被漏掉。

## 4. 角色与权限

| 角色 | 可看状态横幅 | 可改提醒设置 |
|---|---|---|
| `ELDER` | ❌（老人端**永远不显示异常状态**） | ❌ |
| `CAREGIVER_READONLY` | ✅ | ❌ |
| `CAREGIVER_EDITOR` | ✅ | ✅ |
| `RESEARCHER` | ✅（匿名） | ❌ |

**老人端永不显示状态。** 这条没有例外——包括 P3（已诊断 MCI、主动想看趋势）。P3 看的是趋势图，不是状态横幅。状态横幅本质是"判断"，趋势是"数据"。

## 6. 状态管理

```
StatusViewModel
├── status：来自 GET /v1/status/{subjectId}（TTL 5 分钟）
├── copy：从 ui/copy/ 按 copyKey 取
└── actionRoute：按 statusCode 决定（S5 → family/medical，S6 → 无）

ReminderViewModel
├── reminderTime：本地设置 + 云端同步
├── reminderTarget：ELDER | CAREGIVER
├── consecutiveMissedDays：来自服务端
└── currentFrequency：由 consecutiveMissedDays 推导
```

### 6.1 降频规则（FR-4.4）

| 连续未录天数 | 提醒频率 |
|---|---|
| 0–2 天 | 按设定时间每天一次 |
| 3–6 天 | 隔天一次 |
| ≥7 天 | 每周一次 |

**降频是自动的，不可由用户关闭。** 原因：连续未录说明提醒已经造成压力，加频只会更糟。

**家属端同步提示**：连续 3 天未录时，家属端出现提示"最近 3 天没有记录，可以打个电话问问他"，并提供"帮他录"入口（UC-09）。

## 7. 接口依赖

| 用途 | 接口 | 文件 |
|---|---|---|
| 状态 | `GET /v1/status/{subjectId}` | `../../api/API-03-指标与趋势.md` |
| 提醒设置读写 | `GET/PUT /v1/subjects/{id}/reminder` | `../../api/API-04-记录与事件.md` |
| 未录天数 | 含在 status 响应中 | 同上 |

**推送**：老人端用本地通知（不依赖服务端推送，避免国产 ROM 杀后台导致收不到）；家属端用服务端推送。

---

## 8. 异常状态与降级

| 异常 | 表现 | 降级 |
|---|---|---|
| 状态接口失败 | 显示上次成功状态 + "可能不是最新" | 不显示 S0（避免误导为"没记录"） |
| 文案 key 未找到 | **渲染失败并抛出**（构建期应已被扫描拦截） | 不显示兜底文案（兜底文案会绕过禁用词检查） |
| 推送权限未授予 | 家属端提示开启；老人端不提示 | 不影响主流程 |
| 通知被系统拦截 | 家属端显示"老人手机可能未收到提醒" | — |
| S5 但数据已过期 | 显示状态 + 明确的时间标注 | 不隐藏状态 |

## 9. 响应式与可访问性

| 项 | 要求 |
|---|---|
| 横幅高度 | 自适应，文案换行不截断 |
| 字号 | 跟随系统；200% 不截断 |
| 对比度 | 状态文字 ≥4.5:1；竖条 ≥3:1 |
| 色觉障碍 | **状态名必须有文字**，颜色只是辅助 |
| TalkBack | 横幅整体可读，非疾病解释不被跳过 |
| 老人端 | 状态相关组件**不注册进老人端导航树** |

## 11. 验收标准

- [ ] 7 个状态均能正确渲染，颜色与竖条一致（FR-4.1）
- [ ] **全站无红色**；最高级只用深橙（FR-4.2）
- [ ] 文案中无"立即 / 尽快 / 危险 / 严重 / 警告"（FR-4.2）
- [ ] S4/S5 文案**必含非疾病解释**，视觉比重 ≥1/3（FR-4.3）
- [ ] 非疾病解释缺失时组件**渲染失败**（机制保障，非人工检查）
- [ ] 前端**无任何状态判定代码**，只渲染服务端结果
- [ ] 状态降级时文案**不出现"好转/恢复"**
- [ ] 连续 3 天未录自动降频，且不可被用户关闭（FR-4.4）
- [ ] 连续 3 天未录时家属端出现提示 + "帮他录"入口
- [ ] 老人端**任何页面都不出现状态横幅**
- [ ] 老人端提醒走本地通知，不依赖服务端推送
- [ ] 状态文字可被色觉障碍用户分辨
