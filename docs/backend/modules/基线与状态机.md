# 后端模块：基线与状态机

**覆盖需求**：FR-3（基线与趋势）、FR-4（状态与提醒）
**对应接口**：`../../api/API-03-指标与趋势.md`

> **⚠️ 2026-09-28 变更（B2）**：老人端"我想看趋势"开关**彻底移除**，`GET /v1/metrics/{subjectId}/plain` 接口**删除**。老人端无任何指标/趋势接口；趋势与状态仅供家属端查看。S0–S6 状态机本身**保留不变**（同日决策：靠"与个人基线比较、非疾病解释、无诊断用语"支撑合规）。

---

## 1. 职责边界

### 1.1 职责

维护每个被记录者的个人基线，计算指标趋势，并输出状态机结果（S0–S6）与**文案 key**。

**这是全产品唯一产生"判断"的地方。** 前端的克制、合规文案、非疾病解释——全都建立在这个模块的输出之上。

### 1.2 不做什么

| 不做 | 理由 |
|---|---|
| **不输出任何面向用户的文字** | 只输出 `statusCode` + `copyKey`，文案在前端（改文案不发版） |
| **不输出概率、评分、风险等级** | X-1 |
| **不做跨人比较**（常模、同龄人平均） | 只做个人纵向比较 |
| 不做预测、不做外推 | 预测即诊断 |
| 不做"是否异常"的二元判定 | 只输出"与个人基线的关系" |
| 不做量表分数关联 | 量表只在研究模式，且不参与状态计算 |

## 2. 领域对象

```
Baseline
├── subjectId
├── metricKey          # SPEECH_RATE | PAUSE | VOCAB | COHERENCE
├── windowStart / windowEnd
├── mean
├── stdDev
├── sampleCount        # 参与计算的样本数
├── isEstablished      # 是否已建立（≥4 条有效记录）
└── updatedAt

MetricPoint
├── recordId
├── subjectId
├── metricKey
├── value              # 原始数值（服务端内部使用）
├── zScore             # 相对基线（内部使用，前端不展示）
├── qualityFlag        # 只有 VALID 参与趋势
└── recordedAt

StatusSnapshot
├── subjectId
├── statusCode         # S0..S6
├── copyKey            # status.s0 .. status.s6
├── validRecordCount
├── nonDiseaseKey      # 非疾病解释文案 key（S4/S5 必需）
├── since              # 该状态起始时间
└── computedAt

EventTag
├── recordId
├── type               # COLD | MOVE | HOSPITAL | TRAVEL | OTHER
├── note
└── createdBy
```

### 2.1 `zScore` 的存在与边界

`zScore` 存在，但**只用于服务端内部的状态判定与调试**。它：
- 不出现在任何接口响应中（`../../api/API-03-指标与趋势.md` 明确不返回）
- 不出现在日志中
- 不出现在导出文件中

这是"内部可以有数值，外部永远看不到"的落地。

## 3. 基线规则（FR-3.1）

| 规则 | 内容 |
|---|---|
| 建立条件 | 前 14 天或前 4 次**有效**记录，取先到者 |
| 建立后更新 | 28 天滚动窗口 |
| 未建立时 | 全部指标标"数据不足"，**不画折线** |
| 样本不足 | `isEstablished = false`，状态强制 S1 或 S3 |
| 有效样本定义 | `qualityFlag = VALID` 且指标非 `null` |

### 3.1 声学与文本指标的基线要分开算

| 指标 | 依赖 | 基线建立速度 |
|---|---|---|
| `SPEECH_RATE` / `PAUSE` | 声学（本地算） | 快，几乎每条都有 |
| `VOCAB` / `COHERENCE` | 文本（需 ASR） | 慢，ASR 失败则该条不参与 |

**后果**：可能出现"声学基线已建立、文本基线未建立"的中间状态。接口必须能表达这个状态，前端必须能分别呈现。

**设计决定**：`GET /v1/metrics/{subjectId}/baseline` 按 `metricKey` 分别返回 `isEstablished`，不用一个总开关。

### 3.2 任务类型必须同质比较

`DAILY_FREE` 与 `WEEKLY_PICTURE` 的语速天然不同（图片描述是任务驱动，自由叙述是自发）。**基线必须按 `taskType` 分组计算**，否则会把任务差异误判为变化。

这是最容易出错的地方之一，也是"为什么产品轨与研究轨要分开"的技术原因。

## 4. 状态机（FR-4.1）

### 4.1 七个状态

| 状态 | 条件 | `copyKey` | 非疾病解释 |
|---|---|---|---|
| S0 | 0 条有效记录 | `status.s0` | 不需要 |
| S1 | 1–3 条有效记录 | `status.s1` | 不需要 |
| S2 | ≥4 条且无越界 | `status.s2` | 不需要 |
| S3 | 有效记录 <4 条，或仅单项轻度偏离 | `status.s3` | 不需要 |
| S4 | 连续 3 次（或 2 周内 3 次）≥1 项核心指标低于基线 1.5SD | `status.s4` | **必需** |
| S5 | 连续 4 周多指标同向下降 | `status.s5` | **必需** |
| S6 | 家属手动标记已就医 | `status.s6` | 不需要 |

### 4.2 升级规则（缓慢）

```
S0/S1 ──有效记录 ≥4──▶ S2
S2 ──连续 3 次越界──▶ S4        （跳过 S3，S3 是"数据不足"分支）
S4 ──持续 4 周多指标同向──▶ S5
任意 ──家属标记已就医──▶ S6
```

**升级必须缓慢，这是产品最重要的设计决策之一。** 理由（`../../PROJECT_REQUIREMENTS.md` 2.2）：一次误报 = 永久流失。

### 4.3 降级规则（自动）

| 触发 | 降级到 |
|---|---|
| 回到基线范围 | S2 |
| 有效记录 <4 条 | S3（**强制**，不保留 S4/S5） |
| 连续 4 周无越界 | S2 |

**不保留"历史最高状态"。** 状态描述的是"现在"，不是"曾经"。

### 4.4 非疾病解释（FR-4.3）

S4 与 S5 **必须**返回 `nonDiseaseKey`，对应文案如：

> "这可能只是累了，也可能是最近说话变少。"

**服务端硬校验**：`statusCode ∈ {S4, S5}` 且 `nonDiseaseKey` 为空时，**接口返回 500 并告警**，不返回不完整数据。

**为什么用 500 而不是返回空**：宁可让页面挂掉被立刻发现，也不能让一条没有非疾病解释的"变化"提示流到用户面前。这是刻意选择的失败方向。

## 6. 事务与幂等

| 操作 | 事务 | 幂等 |
|---|---|---|
| 重算基线 | 基线 + 更新时间 | 同 subjectId 重复计算覆盖 |
| 重算状态 | 状态快照 + 状态变更记录 | 天然幂等（幂等函数） |
| 写事件标注 | 标注 + 审计 | 需 `Idempotency-Key` |
| 手动标 S6 | 状态 + 审计 | 幂等 |

**重算必须可重复执行且结果一致。** 因为：分析完成、记录删除、事件增删都会触发重算。如果重算不幂等，会出现状态抖动。

**实现要求**：状态计算写成**纯函数** `computeStatus(有效记录列表, 基线, 事件) → statusCode`，不依赖当前状态。这样重算就是安全的。

---

## 7. 队列

| 任务 | 触发 | 说明 |
|---|---|---|
| `recomputeBaseline` | 分析完成、记录删除、质量标记变更 | 异步，可合并（同一 subjectId 短时间多次触发只跑一次） |
| `recomputeStatus` | 基线更新后 | 同步在基线任务内完成即可，不必单独入队 |
| `dailySweep` | 定时（每日） | 检查状态降级（如 S4 连续 4 周无越界 → S2）、到期清理提醒 |

**合并策略**：同一 `subjectId` 的重算任务在 5 秒窗口内合并，避免批量导入时反复重算。

## 8. 缓存

| 键 | 内容 | TTL | 失效 |
|---|---|---|---|
| `baseline:{subjectId}:{metricKey}` | 基线 | 5 分钟 | 重算后主动删除 |
| `status:{subjectId}` | 状态快照 | 5 分钟 | 重算后主动删除 |
| `series:{subjectId}:{metricKey}:{range}` | 趋势序列 | 5 分钟 | 新记录后删除 |

## 9. 审计

| 事件 | 记录 |
|---|---|
| 状态变更 | subjectId、from、to、触发原因（不记录具体数值） |
| 手动标 S6 | 操作者、时间 |
| 事件标注增删 | 操作者、类型、时间 |

**禁止记录**：`zScore`、基线均值与标准差（它们是内部数值，不应出现在日志中）。

---

## 10. 异常处理

| 异常 | 处理 |
|---|---|
| 有效记录不足 | 返回 S1/S3，`isEstablished = false` |
| 基线未建立但请求趋势 | 返回空序列 + `insufficientData: true`，不报错 |
| 文本指标全为 null | 文本类基线 `isEstablished = false`，声学类正常 |
| S4/S5 缺非疾病解释 | **500 + 告警**（4.4） |
| 计算异常 | 返回上一次成功快照 + 告警，不返回错误 |
| 状态抖动（短时间内反复升级降级） | 记录告警；检查重算幂等性 |

## 11. 安全

| # | 要求 |
|---|---|
| 1 | 接口**不返回** `zScore`、基线均值、标准差 |
| 2 | 接口**不返回**任何概率、评分、风险等级 |
| 3 | **老人端无任何指标/趋势接口**（B2）；metrics 路由只对家属端会话开放 |
| 4 | 状态与文案解耦，服务端只给 key |
| 5 | 日志不含内部数值 |
| 6 | 导出文件不含 `zScore` |

## 12. 测试

| 类型 | 覆盖 |
|---|---|
| 单元 | 基线建立边界（3/4 条、14 天）、滚动窗口、升级条件（连续 3 次、4 周）、降级条件 |
| **幂等测试** | 同一批数据重算 100 次，断言状态不变 |
| **任务类型隔离测试** | 混合 `DAILY_FREE` 与 `WEEKLY_PICTURE`，断言基线分组计算 |
| **守卫测试** | S4/S5 且 `nonDiseaseKey` 为空 → 断言 500 |
| **契约测试** | 断言响应中不含 `zScore` / `mean` / `stdDev` / `probability` / `score` 字段 |
| 边界 | 0 条 / 1 条 / 3 条 / 4 条 / 1000 条；全部记录质量不合格 |
| 降级测试 | 有效记录从 5 条降到 2 条，断言状态回落 S3 |

## 13. 验收标准

- [ ] 基线按 `../../PROJECT_REQUIREMENTS.md` 5.3 建立（前 14 天或前 4 次）（FR-3.1）
- [ ] 基线**按 `taskType` 分组**，不混合计算
- [ ] 声学与文本基线**分别**报告 `isEstablished`
- [ ] 基线未建立时返回"数据不足"，不画折线（FR-3.1 / FR-3.3）
- [ ] 状态机 S0–S6 按 4.2 / 4.3 升级降级（FR-4.1）
- [ ] **升级缓慢**：S2→S4 需连续 3 次；S4→S5 需连续 4 周
- [ ] **降级自动**，且不保留历史最高状态
- [ ] 有效记录 <4 条**强制**回落 S3
- [ ] S4/S5 **必返回非疾病解释 key**，缺失时返回 500 并告警（FR-4.3）
- [ ] 状态计算是**纯函数**，重算 100 次结果一致
- [ ] 接口响应**不含** `zScore` / `mean` / `stdDev` / 概率 / 评分（E2E-11）
- [ ] **老人端无任何趋势/指标接口**（B2）；`/plain` 接口已删除，存在性测试断言 404
- [ ] 状态与文案解耦，服务端只返回 `copyKey`
- [ ] 状态变更全部有审计记录
- [ ] 日志与导出文件不含内部数值
- [ ] 批量重算任务按 subjectId 合并，不重复计算
