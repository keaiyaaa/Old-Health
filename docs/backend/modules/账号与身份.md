# 后端模块：账号与身份

**覆盖需求**：FR-5.1、FR-5.5、FR-9.4
**对应接口**：`../../api/API-01-认证与账号.md`

> **⚠️ 2026-09-28 重构**：账号模型由「老人自有账号 + 手机验证码登录」改为
> **「家属邮箱账号 + 绑定码关联老人」**。老人没有账号；老人端会话 = 家属账号 + 选中的老人。
> 本版为重构后的完整设计，旧版（手机号体系）作废。

---

## 1. 职责边界

### 1.1 职责

邮箱注册登录、老人（Subject）创建与绑定、绑定码匹配、老人端选人会话、关系显示（儿子/女儿）、权限判定、同意状态管理。

### 1.2 不做什么

| 不做 | 理由 |
|---|---|
| **不做老人账号** | 老人不注册、不登录；老人设备上用家属账号进入，选择"我是哪位老人" |
| 不做手机号体系 | 注册与找回改用邮箱验证码，登录用密码（2026-09-28 决策） |
| 不做第三方 OAuth | 引入额外数据共享，一期不做 |
| 不做社交关系（好友、关注） | 与产品定位无关 |
| **不做"角色"的客户端声明** | 权限只由服务端按绑定关系判定，客户端传入一律忽略 |
| 不做管理员查看音频的能力 | 数据层就没有 |

### 1.3 新模型一句话

> **账号 = 家属的身份**（儿子/女儿）；**老人 = 被绑定、被选择的主体**。
> 一个账号可绑定多位老人；一位老人可被多个账号绑定（靠「老人名字 + 绑定代码」对齐为同一人）。

## 2. 领域对象

```
Account                  # 家属账号（全产品唯一的账号类型）
├── accountId
├── username             # 账号名，唯一
├── email                # 邮箱（QQ 邮箱等），原文加密存储 + hash 用于登录匹配
├── emailHash            # 不可逆，用于唯一性与登录匹配
├── passwordHash         # 密码哈希（Argon2id），不存明文
├── gender               # MALE | FEMALE
├── relationDisplay      # 派生字段：MALE → 儿子；FEMALE → 女儿（服务端生成）
├── createdAt
└── status               # ACTIVE | DELETING | DELETED

Subject                  # 老人
├── subjectId
├── elderName            # 老人名字（家属绑定输入）
├── bindCodeHash         # 绑定代码哈希（家属自定义，如 123；不可存明文）
│                        # (elderName, bindCodeHash) 唯一 —— 这是多账号对齐同一老人的匹配键
├── displayName          # 展示用昵称（可与 elderName 相同）
├── ageBand              # 年龄段，不存精确生日
├── dialect
├── hearingIssue
├── retentionMonths
└── createdByAccountId   # 首次创建者（仅审计用，不构成特殊权限）

CareLink                 # 账号 ↔ 老人 绑定关系（替代原 Binding）
├── linkId
├── accountId
├── subjectId
├── relationDisplay      # 绑定生效时的关系显示（儿子/女儿快照）
├── createdAt
└── revokedAt            # 非空即已解绑

Consent                  # 同意记录（结构不变）
├── consentId
├── ownerType            # ACCOUNT | SUBJECT —— 挂载层级（schema 关键字段，见 2.2）
├── accountId            # ownerType = ACCOUNT 时必填
├── subjectId            # ownerType = SUBJECT 时必填
├── type                 # PRODUCT | SENSITIVE | ELDER_INFORMED | RESEARCH
├── grantedAt / revokedAt / version / evidenceRef
```

### 2.2 Consent 的挂载层级（schema 规则，2026-09-28 用户决策：全部挂账号）

**所有同意记录统一挂账号（`ownerType = ACCOUNT`）**，一张表实现：

| 类型 | 挂载 | 授予 | 撤回 |
|---|---|---|---|
| `PRODUCT` | 账号 | 注册时自动授予 | 不可撤回（撤回即注销，走 API-05） |
| `SENSITIVE` | 账号 | **仅老人端会话**（老人设备上、老人在场时为该账号授予） | 账号本人 |
| `ELDER_INFORMED` | 账号 | **仅老人端会话**（同上） | 账号本人 |
| `RESEARCH` | 账号 | 研究模式，见 `研究数据管理.md` | 账号本人 |

**校验规则**：访问某老人的敏感数据 = 校验**请求账号**的 `SENSITIVE` 同意有效（不再按 subjectId 校验）。同一账号绑定多位老人时，一次授予覆盖其全部绑定老人；多家属共看同一老人时，**每个账号需各自完成老人在场的授予**。

**设计取舍记录**：挂账号的代价是"同意"与"老人"解耦（数据模型上不再区分是替哪位老人授的）；换来的是 schema 与校验逻辑简单。合规上以"授予场景限定在老人端会话、老人在场"来保住"老人本人的意思表示"。

### 2.1 关键设计

**① 性别 → 儿子/女儿**：注册时选择男女，服务端据此生成 `relationDisplay`。老人端展示绑定家属时，一律显示"儿子"或"女儿"，不显示真实姓名（老人端只见关系称呼，家属端只见老人名字，双向都最小暴露）。

**② 绑定码匹配规则（2026-09-28 用户决策）**：

```
家属绑定老人时输入：老人名字 + 自定义绑定代码

匹配逻辑：
  已存在 (elderName, bindCodeHash) 相同的 Subject
    → 绑定到该 Subject（多家属共看同一位老人，数据互通）
  不存在
    → 新建 Subject，输入者即第一位绑定账号

示例：A 账号绑定父亲，输入「李华 + 123」→ 创建 Subject「李华」
      B 账号输入「李华 + 123」→ 绑定到同一位老人 ✅
      B 账号输入「李华 + 345」→ 新建另一位老人（代码不同 = 不同人）
```

**安全要求（2026-09-28 更新：不支持自定义）**：绑定代码**一律由服务端系统生成**（8 位字母数字强码，去除易混淆字符），**不接受用户自定义**（杜绝 123 这类弱码）。哈希存储；创建老人时**仅返回一次**（后续不可再查看，由家属自行保存并分享给其他家属）；绑定接口按账号 + IP 限流（防枚举）。绑定代码与 `elderName` 一经创建即不可修改（它们是匹配键，改动会拆散多家属的对齐关系）；展示名 `displayName` 可随时修改。

**③ 双向对应**：老人端登录后展示的候选 = 该账号全部有效 CareLink 的老人名字；家属端列表 = 同一集合。选中老人后，该设备会话的一切数据操作都归属该 subjectId——**这是"老人端数据准确传入家属端"的保证机制**。

## 3. 状态机

### 3.1 账号状态

```
ACTIVE ──注销申请──▶ DELETING ──7 天冷静期结束──▶ DELETED
   ▲                    │
   └────冷静期内登录────┘
```

| 状态 | 行为 |
|---|---|
| `ACTIVE` | 正常使用 |
| `DELETING` | 登录后提示可撤销注销；数据停止被读取（除本人） |
| `DELETED` | 不可恢复；按第 6 节规则处理其绑定的老人数据 |

### 3.2 绑定状态

```
ACTIVE ──解绑──▶ REVOKED
```

原 PENDING（邀请）状态取消——绑定码机制下绑定即时生效。**解绑必须立即失效访问**，包括已签发的音频签名 URL（缓存主动失效）。

### 3.3 老人端设备会话（新增）

```
未选择 ──选中某位老人──▶ 已选择(subjectId) ──切换老人──▶ 重新选择
```

- 登录成功后若该账号存在有效绑定，**必须先选老人**才能进入录音等功能
- 会话与 subjectId 绑定后，所有请求在服务端强制限定该 subjectId（防会话内越权到其他老人）
- 切换老人 = 重新选择，产生新的会话绑定

### 3.4 多会话语义（2026-09-28 补）

同一个家属账号的典型使用形态：**登在爸妈两台老人设备上（各锁一位老人）+ 自己手机上（家属端）**。

| 规则 | 内容 |
|---|---|
| 并发会话 | **允许**，每账号并发会话上限 **5**（超限登录时吊销最久未活跃的会话并提示） |
| 会话独立性 | 每个会话独立锁定 subjectId（或家属端不锁定），互不干扰 |
| 同账号两台设备锁**不同**老人 | 允许（典型场景：一台设备给爸用、一台给妈用） |
| 同账号多台设备锁**同一**老人 | 允许（备用机 / 换机过渡期），录音归属同一 subject，数据不冲突 |
| 会话可见 | `sessions` 表（refresh token 有状态，README 8.6）支持按账号列出全部活跃会话、单独踢出 |

## 4. 权限

### 4.1 权限判定是**服务端**的唯一职责

客户端传入的任何角色、任何 `subjectId` 都不可信。判定流程：

```
1. 令牌 → accountId
2. accountId + subjectId → 查 CareLink（有效绑定？）
3. 老人端设备会话：会话绑定的 subjectId 必须 = 请求的 subjectId
4. 权限矩阵 → 不通过 → 返回 404
```

### 4.2 权限判定的入口

| 入口 | 用途 | 说明 |
|---|---|---|
| `canAccess(accountId, subjectId)` | 是否能看该老人数据 | 有效 CareLink 即可 |
| `canWrite(accountId, subjectId)` | 是否能写（录音登记、标注、设置、删除） | 有效 CareLink 即可（一期不区分只读/编辑，原 CG_READONLY/CG_EDITOR 细分取消） |
| `requireRole(accountId, role)` | 系统角色断言（RESEARCHER / OPS_ADMIN） | 与家属账号身份正交 |

### 4.2a 系统角色的授予路径（2026-09-28 补，此前缺失）

注册只创建家属账号；`RESEARCHER` / `OPS_ADMIN` 是**叠加在账号上的系统角色**（`Account.role` 默认 `FAMILY`）。授予路径：

| 角色 | 一期授予方式 | 审计 |
|---|---|---|
| `FAMILY` | 注册默认 | — |
| `RESEARCHER` | **无自助入口、无 HTTP 接口**。由运维直接操作数据库为指定账号设置角色，操作前记录变更目的 | 角色变更写审计（操作者=运维身份、目标账号、时间、目的），`revokeRole` 同样留痕 |
| `OPS_ADMIN` | 同上 | 同上 |

**为什么不建管理后台 API**：一期单研究者场景，管理面=攻击面。写明"数据库手工 + 强制审计"是这个规模下诚实且安全的选择；将来多中心/多运营时再建后台与接口（届时必须补角色变更幂等与二次确认）。

### 4.3 越权响应

| 情况 | 响应 |
|---|---|
| 资源不存在 | 404 |
| 资源存在但无有效绑定 | **404**（不是 403） |
| 老人端会话请求了非选中老人的资源 | 404 |
| 角色不足（如非研究者访问研究接口） | 404 |

**统一 404 的理由不变**：403 泄露资源存在性。

### 4.4 敏感操作的"本人"规则调整

原设计"删除/撤回同意仅本人"基于老人自有账号。新模型下调整为：

| 操作 | 权限 |
|---|---|
| 删除单条记录 / 清空老人记录 | 任意有效绑定账号（**解绑前的历史行为不可抵赖，全部审计**） |
| 修改老人留存期限 | 任意有效绑定账号 |
| 注销账号 | 账号本人（= 登录者） |
| 撤回 `SENSITIVE` / `ELDER_INFORMED` 同意 | 账号本人（挂账号后语义统一，见 2.2） |

## 5. 注册、登录与绑定流程

### 5.1 注册（邮箱验证码）

```
1. 用户填写：账号名 + 邮箱 + 邮箱验证码 + 密码 + 性别（男/女）
2. 服务端核销验证码（一次性、≤5 分钟有效）
3. 事务内：创建 Account + 初始 PRODUCT 同意记录
4. relationDisplay 按 gender 派生（儿子/女儿）
```

**验证码只在两个场景发送**：① 注册验证邮箱；② 忘记密码重置。**日常登录不发验证码，用密码。**

### 5.2 登录

```
账号名或邮箱 + 密码 → 短期 access token + 长期 refresh token
```

| 客户端 | 登录后行为 |
|---|---|
| 老人端 | 弹出该账号绑定的老人名字列表 → 选择 → 进入对应老人的工作台 |
| 家属端 | 直接进入；首页为老人列表，点谁看谁（列表切换） |

### 5.3 绑定老人

```
家属端：输入老人名字 + 绑定代码（系统生成的 8 位强码，由首位创建家属分享）
  → (elderName, bindCodeHash) 匹配既有 Subject？
      ├─ 命中 → 创建 CareLink，绑定既有老人（数据互通）
      └─ 未命中（或未提供代码）→ 新建 Subject，系统生成绑定代码，仅本次返回
  → 审计 + 清理相关权限缓存
```

> 绑定代码**不支持自定义**（2026-09-28 决策）：一律系统生成，创建时仅返回一次。

### 5.4 事务与幂等

| 操作 | 事务范围 | 幂等 |
|---|---|---|
| 注册 | 账号 + 初始同意 + 验证码核销 | 邮箱/账号名唯一约束 |
| 绑定（命中既有老人） | CareLink + 审计 + 缓存失效 | 重复绑定返回已有 CareLink |
| 绑定（新建老人） | Subject + CareLink + 审计 | **并发同 (name,code) 需唯一约束兜底，禁止产生两个 Subject** |
| 解绑 | CareLink.revokedAt + 审计 + 缓存失效 | 天然幂等 |
| 忘记密码 | 验证码核销 + passwordHash 更新 | 验证码一次性 |
| 注销 | Account.status + 入队 cleanup | 天然幂等 |

**禁止在事务内做网络调用**（邮件验证码发送必须在事务外）。

## 6. 账号注销与老人数据的命运（新模型特有的问题）

老人没有账号，其数据归属于绑定关系网。注销规则：

```
账号注销（7 天冷静期结束）：
  1. 该账号全部 CareLink 撤销
  2. 对每个曾绑定的 Subject 检查：是否仍存在其他有效 CareLink？
      ├─ 有 → 老人数据保留（其他家属还在看）
      └─ 无 → Subject 进入 DELETING，入队 purge，硬删除全部老人数据
  3. 账号本体硬删除
```

**这是"数据对应关系"在生命周期上的延伸**：数据跟着老人走，不跟着某一个家属账号走。此规则需在隐私政策中说明。

## 7. 安全要求

| # | 要求 |
|---|---|
| 1 | 邮箱存储：`emailHash`（登录匹配，加盐 HMAC）+ `emailEncrypted`（展示，字段级加密）。**不存明文** |
| 2 | 密码：Argon2id 哈希，不存明文、不可逆；强度要求（长度 ≥8） |
| 3 | 绑定代码：哈希存储；绑定接口按账号 + IP 限流；建议最短 4 位 |
| 4 | 令牌：短期 access token（≤30 分钟）+ 长期 refresh token；refresh token 可单独吊销 |
| 5 | 登录限流：按账号 + IP 双维度；密码错误次数限制 |
| 6 | 邮箱验证码：短时效（≤5 分钟）、一次性、防重放 |
| 7 | 会话：支持多设备（老人端设备 + 家属端手机可同时在线），可单独踢出 |
| 8 | **老人端会话强制锁定 subjectId**：切换老人必须显式重新选择，不允许会话内静默换人 |
| 9 | 同意校验在服务端：涉及敏感信息的接口必须校验 `SENSITIVE` 同意有效 |
| 10 | 审计：绑定/解绑、同意变更、管理员访问、删除操作全部留痕 |
| 11 | 运营管理员在数据层无音频读权限（数据库权限实现，非代码判断） |

## 8. 缓存

| 键 | 内容 | TTL | 失效时机 |
|---|---|---|---|
| `perm:{accountId}:{subjectId}` | 权限判定结果 | 1 分钟 | 绑定变更时主动删除 |
| `links:{accountId}` | 账号的绑定老人列表 | 1 分钟 | 绑定变更时删除 |
| `subject:{subjectId}` | 老人基本信息 | 5 分钟 | 更新时删除 |
| `consent:{subjectId}` | 同意状态位图 | 1 分钟 | 同意变更时删除 |

**同意缓存 TTL 必须短**（1 分钟），撤回同意后的访问窗口是合规红线。

## 9. 审计

| 事件 | 记录字段 |
|---|---|
| 注册 / 登录成功 / 失败 | accountId、IP 摘要、时间、结果 |
| 绑定（新建 / 命中既有） | 操作者、subjectId、是否命中既有老人、时间 |
| 解绑 | 操作者、subjectId、时间 |
| 老人端选择 / 切换老人 | accountId、subjectId、设备标识、时间 |
| 同意授予 / 撤回 | 类型、版本、时间、来源 |
| 删除记录 / 清空 | 操作者、范围、时间 |
| 管理员访问 | 管理员 ID、访问对象、时间、目的 |
| 注销 | 账号、时间、受影响的 Subject 及其处置 |

## 10. 异常处理

| 异常 | 响应 |
|---|---|
| 令牌过期 / 无效 | 401 + `TOKEN_EXPIRED` / `TOKEN_INVALID` |
| 资源无权 | 404 |
| 邮箱或账号名已被注册 | 409 + `EMAIL_TAKEN` / `USERNAME_TAKEN` |
| 密码错误 | 400 + `PASSWORD_WRONG`，累计错误触发限流 |
| 验证码错误 / 过期 | 400 + `CODE_INVALID` |
| 绑定代码限流触发 | 429 + `BIND_RATE_LIMITED` |
| 同意未授予 | 403 + `CONSENT_REQUIRED`（需引导用户同意，此处 403 有业务含义） |
| 老人端未选择老人就请求业务接口 | 400 + `SUBJECT_NOT_SELECTED` |
| 邮件服务失败 | 503 + 可重试；不暴露上游错误 |

| **越权测试** | 枚举所有接口 × 无绑定/已解绑/会话锁外 subject 的组合，断言 404 |
| **会话锁定测试** | 老人端会话请求另一老人资源，断言 404；切换老人后归属正确 |
| **撤权延迟测试** | 解绑后立即请求，断言拒绝 |
| 并发 | 同邮箱并发注册、并发同 (name,code) 绑定（断言只产生一个 Subject） |
| 幂等 | 重复绑定、重复注销 |
| 安全 | 绑定码枚举限流、密码暴力破解、令牌重放、验证码重放 |
| 注销 | 注销后按 6 节规则断言各 Subject 的留存/删除行为正确 |

## 12. 验收标准

- [ ] 注册仅支持：账号名 + 邮箱 + 邮箱验证码 + 密码 + 性别
- [ ] 验证码只在注册与忘记密码场景发送；登录只用密码
- [ ] 邮箱明文不入库（字段级加密 + 哈希匹配）
- [ ] 密码 Argon2id 哈希存储
- [ ] 性别 → 老人端显示"儿子/女儿"，由服务端派生，不显示家属真实姓名
- [ ] 一个账号可绑定多位老人；家属端列表切换查看
- [ ] **绑定码匹配规则生效**：同名同码 = 同一位老人，多账号数据互通；不同码 = 不同老人
- [ ] 并发绑定同 (name, code) 只产生一个 Subject
- [ ] 老人端登录后必须选人，会话锁定 subjectId，切换需显式操作
- [ ] 老人端数据准确归属所选老人，家属端对应可见（端到端对应测试通过）
- [ ] 老人端只显示绑定老人名字，家属端只显示老人名字与关系称呼（最小暴露）
- [ ] 越权返回 404（唯一例外：`CONSENT_REQUIRED` 返回 403）
- [ ] 解绑后访问立即失效（撤权测试通过）
- [ ] 注销按第 6 节规则处置老人数据：仍被他人绑定的保留，无绑定的硬删除
- [ ] 注销幂等，7 天冷静期内可撤销
- [ ] 存储 `ageBand` 而非精确生日
- [ ] 权限判定完全在服务端，客户端传入的角色与 subjectId 一律校验
- [ ] 绑定变更、老人端选人/切换、同意变更、删除、管理员访问全部有审计记录
- [ ] 运营管理员无音频读权限（数据层验证）
