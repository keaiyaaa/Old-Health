# 后端模块：通知与推送

**覆盖需求**：FR-4（状态与提醒——家属触达侧）、FR-5（家属端协作）
**对应接口**：`../../api/API-07-通知与推送.md`
**状态**：2026-09-28 新增（此前 notify 队列只有定义没有落地设计）

---

## 1. 职责边界

### 1.1 职责

把"需要家属知道的事"送达家属设备：状态机升级（S4/S5）、记录完成回执、提醒家属设置的通知。管理推送令牌、生成合规通知文案、维护通知列表。

### 1.2 不做什么

| 不做 | 理由 |
|---|---|
| **不做实时推送**（WebSocket 长连） | 场景是异步通知，准实时即可；一期用厂商推送通道 + 客户端轮询兜底 |
| **通知文案不含任何数值** | 合规红线：指标数值、`zBand`、"异常/风险"字样一律不出现（见第 4 节） |
| 不做短信通知 | 成本高、易被标记骚扰；一期只用 App 推送 + 应用内通知中心 |
| 不做通知的社交化（回复、已读回执给老人看） | 工具定位 |
| 不做营销/运营推送 | 合规：通知仅限产品功能必需 |
| **不做老人端录音提醒**（2026-09-28 补） | 每日/每周"该录音了"的提醒**纯客户端本地通知**（本地定时 + 降频规则，见 `../../frontend/modules/录音采集与上传.md`），服务端不参与、不入通知中心——少一个功能面，老人设备也无网络依赖 |

## 2. 领域对象

```
DeviceToken                 # 推送令牌
├── tokenId
├── accountId
├── clientId                # 设备标识（与登录 deviceId 关联）
├── channel                 # HUAWEI | XIAOMI | OPPO | VIVO | FCM | APNS | POLLING
├── pushToken               # 厂商通道令牌（加密存储）
├── createdAt
└── revokedAt

Notification                # 通知（应用内通知中心 + 推送共用数据源）
├── notificationId
├── accountId               # 收件家属账号
├── subjectId
├── type                    # STATUS_CHANGED | RECORD_DONE | REMINDER
├── copyKey                 # notify.s4.changed 等（文案在前端，服务端只给 key）
├── params                  # 占位符（如 {elderName}），不含数值
├── createdAt
└── readAt                  # 非空即已读
```

## 3. 触发矩阵（谁在什么情况下给谁发什么）

| 触发源 | 事件 | 收件人 | `copyKey` 示例 |
|---|---|---|---|
| 基线与状态机 | S2 → S4 升级 | 全部有效绑定账号 | `notify.status.s4` |
| 基线与状态机 | S4 → S5 升级 | 同上 | `notify.status.s5` |
| 分析流水线 | 记录分析完成（DONE） | 全部有效绑定账号（可按提醒设置关） | `notify.record.done` |
| 分析流水线 | 记录降级（仅声学指标） | 同上 | `notify.record.degraded` |
| 定时任务 | 连续 N 天未记录提醒 | 全部有效绑定账号 | `notify.reminder.norecord` |

**不发的事件**：S0–S3 之间的变化（数据充分度变化不推送，避免打扰）；降级（状态回落）**不推送**——升级缓慢、降级安静的既有设计延伸到通知侧。

## 4. 文案合规（本模块的红线）

| # | 规则 |
|---|---|
| 1 | 服务端只发 `copyKey` + 占位符（`{elderName}`），**不拼文案、不含数值** |
| 2 | 通知栏/横幅文案**禁止出现**：指标数值、`zBand`、"异常""风险""下降"等判断性词汇 |
| 3 | 允许的表述："爸爸本周有新的记录变化，点开看看""妈妈刚完成一次录音" |
| 4 | 点开通知 → 跳转家属端对应页面 → 页面内按既有合规文案展示（S4/S5 含非疾病解释） |
| 5 | 文案模板版本化（`copyKey` + version），改文案不发版只改前端资源 |

**为什么这么严**：通知是用户被动看到的界面。如果推送横幅写"妈妈语速异常下降"，等于绕过了页面内全部合规设计，直接构成"病情判断"。

## 5. 渠道策略（一期）

```
优先级：厂商推送通道（华为/小米/OPPO/vivo，按设备品牌路由）
       ↓ 通道不可用 / 令牌失效
兜底：客户端前台轮询 GET /v1/notifications（打开 App 时拉取 + 前台每 15 分钟）
```

| 要求 | 说明 |
|---|---|
| 聚合服务 | 一期用境内聚合推送服务（极光/个推类）或厂商直连，**二选一待定**，接口层先抽象 `PushProvider`（与 ASRProvider 同模式，选型只换 adapter） |
| 令牌管理 | 登录设备注册、登出/踢出时吊销；一设备一 token |
| 失败处理 | 推送失败**不重试到成功**：走 notify 队列既有重试（3 次），耗尽进死信告警；应用内通知中心始终兜底可见 |
| 免打扰 | 客户端本地决定展示时段；服务端不设计免打扰（保持简单） |

---

## 6. 事务与队列

| 操作 | 说明 |
|---|---|
| 生成 Notification | 与状态重算/分析完成**同一事务**内写库（保证"页面可见"与"通知可达"一致） |
| 入队 notify 任务 | 事务性发件箱（同 README 5.4），发布者投递到 `notify` 队列 |
| notify 队列 | 最多 3 次、指数退避；死信告警（README 5.5 既有设计） |
| 幂等 | 同一事件重复入队：以 `(type, subjectId, 触发批次 id)` 幂等，重复投递不重复推送 |

## 7. 权限

| 操作 | 校验 |
|---|---|
| 注册/吊销推送令牌 | 已认证（本人账号） |
| 查询通知列表 | 已认证（只返回本人 accountId 的通知） |
| 标记已读 | 已认证（本人通知） |
| 通知涉及的老人 | `canAccess`（收件时已校验绑定；解绑后历史通知保留但跳转页面返回 404） |

## 8. 测试

| 类型 | 覆盖 |
|---|---|
| 单元 | copyKey 占位符渲染（断言无数值泄漏）、触发矩阵全组合 |
| **红线测试** | 全部通知 payload 扫描数值/禁词，命中数为 0 |
| 集成 | S2→S4 升级 → Notification 落库 → 入队 → Mock 推送 → 已读 全链路 |
| 幂等 | 同一事件重复入队，断言只推一次 |
| 降级 | 推送通道不可用，断言应用内通知中心仍可见 |
| 解绑 | 解绑后旧通知点击跳转，断言页面 404 |

---

## 9. 验收标准

- [ ] S4/S5 升级触发通知，S0–S3 变化与降级**不**触发
- [ ] 通知 payload 只含 `copyKey` + 占位符，**无数值、无判断性词汇**（红线测试通过）
- [ ] 厂商通道按设备品牌路由，不可用时轮询兜底
- [ ] 推送失败走队列重试 3 次，死信告警；应用内通知中心始终兜底
- [ ] 通知与状态重算同事务落库，幂等不重推
- [ ] 通知列表游标分页，只返回本人通知
- [ ] 解绑后历史通知保留但跳转 404
- [ ] 登出/踢出设备时推送令牌吊销
