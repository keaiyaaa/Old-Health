> **文档保留不删** —— 它是一份真实做过的平台可行性评估。如果将来确实要上小程序，下面 9 条平台约束（P1–P9）和 3 个阻断点（B1–B3）可以直接复用，不用重做一遍。

## 0. 一句话结论

小程序**能**承载家属端全部功能和老人端录音主流程，但会永久失去三条**已经写进验收标准**的能力：
断网全流程可用（FR-6.1 / E2E-02）、后台与息屏录音、崩溃后自动保存音频（FR-1.4）；
同时老人端提醒必须从「系统本地通知」改为「微信订阅消息」，其可用性**取决于服务类目能否申请下来**。

这不是实现质量问题，是平台能力边界。换任何团队、任何框架（原生小程序 / uni-app / Taro）都绕不过去。

**另一个必须知道的事实**：本项目 v1.0 版需求设计说明书本来就是按微信小程序写的（该文件现已不存在），当时已经明确记录：

> 缺点：小程序录音时长受限、后台录音受限、本地存储受限 → **二期上原生 App 做长录音和离线**，小程序保留为家属端

也就是说，这个结论**项目自己已经得出过一次**，后来被「原生 Android App」的决策覆盖了。现在转回小程序，等于把当时识别出的三处缺口重新接受一遍。区别是：当时没有 FR-6.1、FR-1.4 这类成文的验收标准，现在有了。

## 1. 本次评估的依据（已核实，非记忆）

| # | 平台约束 | 对本项目的影响 | 出处 |
|---|---|---|---|
| P1 | 小程序进入后台约 **5 秒**后微信停止其 JS 线程执行，进入「挂起」 | 录音期间切走微信、息屏、接电话 → 录音链路中断 | 微信官方《运行机制》 |
| P2 | 录音走 `wx.getRecorderManager`，结果落到**临时文件**（`tempFilePath`），无流式落盘接口 | 做不到「录音中每 2 秒 flush」，进程被杀即丢已录内容 | 官方 `RecorderManager` 文档 |
| P3 | 录音中断事件（`onInterruptionBegin`）官方只覆盖**微信语音 / 视频聊天** | 系统来电、其他 App 占用麦克风不在覆盖范围，异常处理更难做全 | 官方 `onInterruptionBegin` |
| P4 | 本地缓存上限 **10MB**，单个 key 上限 **1MB** | 音频不可能本地缓存（60 秒 AAC 约 1MB+）；「本地为写入真源」架构不成立 | 官方《存储》 |
| P5 | 无本地定时通知 / 闹钟能力 | 老人端提醒必须改走订阅消息 | 平台无此 API |
| P6 | 订阅消息分**一次性**（全体可用）与**长期**（仅对政务民生、**医疗**、交通、金融、教育开放） | 想要「订阅一次、长期提醒」→ 必须拿到医疗类目 | 官方《订阅消息》 |
| P7 | 医疗健康类目下「就医服务」要求《医疗机构执业许可证》 | 无医疗资质主体**可能拿不到**该类目，进而拿不到长期订阅 | 官方《法规依据及示例》 |
| P8 | 2023-09-15 起，未在后台配置《用户隐私保护指引》并适配相关接口的，**对应接口不可用** | 录音、存储、上传等接口需先过隐私协议 | 官方《小程序隐私协议开发指南》 |
| P9 | 2024 年起小程序须完成 **ICP 备案**才能上架 | 排期前置项，通常数周 | 官方《小程序备案操作指引》 |

> 类目与资质要求会随政策变动，官方文档明确「以提交时所要求的材料为准」。P7 需要在正式提交类目时再确认一次。

## 2. 影响矩阵

### 2.1 原样保留（不受影响）

| 资产 | 说明 |
|---|---|
| 状态机 S0–S6 与全部文案纪律 | 纯服务端 + 文案层，与端无关 |
| 指标字典与 `zBand` 契约（`../api/API-03-指标与趋势.md`） | 接口契约与端无关 |
| 家属端信息架构与全部页面 | 小程序完全能承载 |
| 白 + 绿视觉规范、老人端零指标 / 零趋势 | 设计层资产，直接复用 |
| 后端 API 契约（除少量字段） | 与端无关 |
| 「App 只搬运数据、不做解读」的合规设计 | 与端无关 |

### 2.2 必须改造

| 模块 | 原设计 | 小程序下的做法 | 涉及文档 |
|---|---|---|---|
| **录音采集** | `MediaRecorder` 直接写入 app 私有目录加密文件 | `wx.getRecorderManager` → 临时文件 → **立即上传**；无本地落盘 | `../frontend/modules/录音采集与上传.md` |
| **上传队列** | `WorkManager` 持久化任务，可延迟、可重试、重启继续 | 无后台任务框架。只能在**前台**上传，失败需用户下次进入时重试 | 同上 |
| **本地缓存** | Room + SQLCipher | 无数据库。`wx.setStorage` 10MB / 单 key 1MB，只能存轻量元数据 | 同上、`../PROJECT_REQUIREMENTS.md` FR-6.2 / NFR-1.2 |
| **音频加密** | `EncryptedFile`（AES-GCM） | 无文件系统访问权。临时文件由微信托管，加密存储无从谈起 | `../PROJECT_REQUIREMENTS.md` FR-6.2 |
| **老人端提醒** | 系统本地通知（断网也能响） | 微信订阅消息（服务端下发，需用户订阅） | `../frontend/modules/状态与提醒.md` §7 |
| **登录与账号** | 手机号 / 账号密码 | `wx.login` → `openid`；手机号需「手机号快速验证」组件（按次计费） | `../api/API-01-认证与账号.md`、`../backend/modules/账号与身份.md` |
| **导出与分享** | 生成 PDF 文件保存 / 分享 | 小程序内可生成文件并 `wx.openDocument` / 转发给微信好友，**不能任意写入用户文件系统** | `../frontend/modules/就医衔接与数据导出.md` |
| **声学指标计算位置** | 端侧本地计算（≤5 秒出结果） | 小程序算力与 WASM 支持有限，建议**整体移到云端**（与已定的云端 ASR 合并成一条流水线） | `../backend/modules/分析流水线.md` |
| **测试与真机验证** | MIUI / HarmonyOS / ColorOS / OriginOS 后台限制测试 | 改为微信版本 × 基础库版本 × 机型矩阵；后台行为由微信统一决定，测试面反而变小 | `../frontend/modules/录音采集与上传.md` §9 |

### 2.3 不可实现（需从验收标准中删除或降级）

| 原能力 | 出处 | 小程序下的实际情况 |
|---|---|---|
| **断网状态下完成录音全流程，无任何功能降级** | FR-6.1 / E2E-02 | **不可能。** 音频无法本地留存，断网时录音完成后必须挂在临时文件里等待网络，而临时文件的存活期不由我们控制。只能降级为「断网时可录，但必须提示用户保持在小程序内直到上传完成」 |
| **后台 / 息屏录音** | 隐含在 FR-1.3（最长 5 分钟） | **不可能。** 后台 5 秒挂起 |
| **录音中断 / 闪退后已录部分可恢复** | FR-1.4 | **不可能。** 无流式落盘 |
| **本地音频加密存储** | FR-6.2 | **不可能。** 无文件系统访问权 |
| **打开即录音 ≤2 次点击** | FR-1.1 | **存疑。** 老人需先打开微信 → 找到小程序 → 进入页面 → 点录音。可通过「添加到我的小程序 / 桌面」缓解，但比原生 App 多一层，需实测 |
| **老人端「零技术失败感知」** | `../frontend/modules/录音采集与上传.md` §7 降级原则 | **压力变大。** 上传失败不再有后台自动重试兜底，老人可能被要求「重试」，与「老人端只呈现好消息」冲突 |

## 3. 三个真正的阻塞点

### B1. 老人端提醒机制（影响最大）

原设计把老人端提醒压在**系统本地通知**上，理由写得很清楚：不依赖服务端推送，避免国产 ROM 杀后台。

小程序没有这条路。只剩订阅消息，而它有两个硬性前提：

1. **一次性订阅**：用户每点一次「允许」，开发者只能下发**一条**消息。老人端每天提醒 → 需要老人每天点一次订阅，对 78 岁用户不可行。
2. **长期订阅**：订阅一次可长期下发，但**仅对政务民生、医疗、交通、金融、教育等类目开放**。想走这条路 → 必须先拿到**医疗健康类目** → 而该类目下有资质门槛（见 B3）。

**这是一个闭环依赖**：老人端能不能收到提醒 → 取决于订阅消息模式 → 取决于服务类目 → 取决于主体资质。

如果拿不到医疗类目，只剩三条路：
- 提醒只发给**家属**（家属端是普通服务通知，一次性订阅可覆盖），由家属打电话提醒老人；
- 小程序内做「打卡提醒」（用户打开小程序才看到），**不构成真正的提醒**；
- 放弃老人端提醒，只保留家属端提示。

### B2. 「音频绝不丢失」这条承诺守不住

`../frontend/modules/录音采集与上传.md` 的核心承诺是：

> **硬规则**：任何一步失败都不影响音频文件已经存在这个事实。

原生 App 靠「先落盘、再处理」+ WorkManager 重试守住这条。小程序下音频只存在于微信托管的临时文件里，落盘、重试、后台续传三件武器全部没有。**这条承诺必须改写成一句更弱的话**，且要写清楚它在什么情况下会破。

这不是可以「后面优化」的技术债，而是要在需求里明确降级的**能力缺口**。

### B3. 类目与资质：决定能不能上架，也决定 B1 能不能解

| 类目 | 资质要求 | 对本项目的意义 |
|---|---|---|
| 医疗健康 → 就医服务 | 《医疗机构执业许可证》 | 通常拿不到（非医疗机构主体） |
| 医疗健康 → 其他二级类目 | 官方以提交时要求为准 | **必须逐一确认**，直接决定长期订阅可用性 |
| 非医疗类目（如工具 / 效率） | 门槛低 | 能上架，但**拿不到长期订阅**，B1 无解 |

**需要动作**：在正式提交类目前，先向微信开放平台确认「一个不提供诊疗、只做语音记录与趋势呈现的健康管理类产品，可以落在哪个二级类目、需要什么材料」。这个答案比技术选型更早决定产品形态。

另需注意：小程序上架前要完成 **ICP 备案**（P9），且要配置《用户隐私保护指引》（P8）。本项目处理的是**声纹 + 医疗健康信息**双重敏感个人信息，隐私指引里必须如实声明，否则接口会被禁用。

## 4. 方案选项

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| **甲：单端小程序** | 老人端 + 家属端都在小程序里 | 单一代码库、老人零安装、家属零成本邀请、开发量最小 | 接受 §2.3 全部能力缺口；老人端提醒依赖类目资质；断网可用性承诺作废 |
| **乙：小程序家属端 + 原生老人端** | 家属端小程序，老人端保留原生 | 老人端录音链路与现有设计**完全一致**，FR-1.4 / FR-6.1 / FR-6.2 全部保留；提醒仍是本地通知 | 两套代码库、两个发布渠道；v1.0 提过的「二期方案」 |
| **丙：小程序单端 + 录音后强制留在前台** | 同甲，但把「录完必须停在小程序里直到上传完成」做成明确的交互 | 把能力缺口显式化，不欺骗自己 | 对 78 岁用户的可用性风险最高，可能直接导致录音失败率上升 |

**我的建议：先按甲做原型与需求（因为你的目标是论文 + 原型设计，甲足够），但在文档里把 §2.3 的缺口写成显式的「平台限制」章节，而不是悄悄删掉验收标准。**
如果后续要做真实用户测试，再评估是否切到乙。理由：论文方向一是「语音/语言 AD 早期筛查」，需要的是**可控的、高质量的录音**；如果小程序录音在真实老人身上失败率高，采到的数据质量会直接伤害论文。
